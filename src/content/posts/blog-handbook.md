本文根据 **2026 年 10 月 25 日**、`C:\code\blog-astro` 中的实际文件编写。以后教程与文件不一致时，以当前文件和终端实际输出为准。示例日期用于演示，新文章应填写自己的实际日期。

## 先走一遍最短路线

“终端”是输入命令的窗口，“PowerShell”是其中理解命令的程序。本文统一用 Windows PowerShell。所有终端命令，除非另有说明，都在项目根目录执行；“文件内容”代码块则复制到编辑器里的文件，**不要粘进终端**。

1. 用 VS Code 的“文件 → 打开文件夹”打开 `C:\code\blog-astro`。
2. 选择“终端 → 新建终端”，确认标签是 PowerShell。逐行输入：

   ```powershell
   Set-Location 'C:\code\blog-astro'
   Get-Location
   git status
   corepack pnpm --version
   ```

   本次环境能运行 `corepack pnpm`，返回 `9.14.4`；单独输入 `pnpm` 会提示找不到命令。因此本文采用已经核实可用的 `corepack pnpm`。如果你以后安装好了独立的 `pnpm`，可以省略 `corepack`。
3. 第一次拿到项目、还没有依赖时，先运行 `corepack pnpm install`。本次已有 `node_modules`，普通写文章不用每次重装。
4. 在同一个 PowerShell 启动预览：

   ```powershell
   $env:ASTRO_TELEMETRY_DISABLED = '1'
   corepack pnpm dev
   ```

   第一行只为当前终端及其子进程关闭 Astro 使用统计，是受限环境遇到遥测写入问题时的处理方式，不是发布开关。
5. 用浏览器打开终端显示的 `Local` 地址，通常是 `http://localhost:4321/`。本篇路径是 `/posts/blog-handbook/`，通常访问 `http://localhost:4321/posts/blog-handbook/`。端口以实际输出为准。
6. 在编辑器打开 `src/content/posts/blog-handbook.md`。第二条 `---` 后面是正文，保存后回浏览器看变化。先保持 `draft: true`。
7. 准备公开时读“一篇文章从写作到上线”。**本地预览成功还不等于上线**；个人远程仓库和部署目前仍待配置。

成功后应看到文章、日期，以及宽屏下由主题自动生成的目录。`src/config.ts` 已启用目录，深度为 2；本文正文从二级标题开始，目录展示二级和三级标题。这里没有另写一份需要手动同步的目录。

如果第一步就失败，先看“终端入门”，不必立刻重新安装整个项目。

## 先认识这个博客

### 源码是食谱，网页是做好的菜

**源码**是我们维护的原材料：文章、图片、配置和程序文件。浏览器需要的是 HTML、CSS、JavaScript 等网页文件，它们是源码加工出的**构建产物**。HTML 管网页结构，CSS 管外观，JavaScript 管需要执行的交互。

构建时，Astro 把文章、页面模板和配置组装成网页，把资源处理好，输出到 `dist/`。部署时把成品交给网站托管服务，访客才可以通过公网地址访问。直接把 Markdown 文件放上网，并不等于完整博客已经做好。

| 名称 | 可以怎样理解 | 在当前项目中的工作 |
| --- | --- | --- |
| Astro | 组装网页的工具 | 读取文章与模板，启动预览，生成网站 |
| Fuwari | 做好的博客框架与外观 | 提供布局、卡片、目录、搜索入口 |
| Markdown | 用少量符号写文章的文本格式 | 用标题、列表、代码块组织正文 |
| Node.js | 让开发工具在电脑上运行的环境 | 运行 Astro 和项目脚本 |
| pnpm | 管理项目依赖的工具 | 安装工具包，执行项目命令 |
| Git | 记录文件版本的工具 | 看改动、提交、比较和恢复历史 |
| GitHub | 托管 Git 仓库的网站 | 保存远程源码，也能配合部署服务 |
| Pagefind | 给静态网站制作搜索目录的工具 | 构建后读取网页，生成搜索索引 |

当前 `package.json` 固定 Astro 为 `5.13.10`，指定 `pnpm@9.14.4`；本地 Pagefind 是 `1.4.0`，Expressive Code 是 `0.41.4`。这是核实记录，不是在建议一键升级。

### 保存、提交、推送和部署是四件事

| 动作 | 发生在哪里 | 结果 |
| --- | --- | --- |
| 保存 | 编辑器 → 本机文件 | `Ctrl+S` 把文字写入磁盘 |
| Git 提交 | 本地 Git 仓库 | 给选定改动保存带说明的版本记录 |
| 推送 | 本地 → 指定远程仓库 | 让远程也拥有这些提交 |
| 部署 | 构建结果 → 网站托管环境 | 让访客访问新的网页成品 |

保存不自动提交，提交不自动推送。推送是否自动部署，取决于托管平台有没有连接正确仓库和分支、构建是否成功。GitHub 上出现文章文件，不证明网站已经更新。

让 AI 帮忙修改时也要先检查文件和 Git 差异，再本地预览。AI 可能误改配置、用错版本的语法，或引用不存在的图片；“回答说完成了”不能代替验证。

│   │   ├── posts/              文章集合

`dist/` 的网页会在下次构建重新生成，手动修改容易丢失。`node_modules/` 里的修改也可能被重新安装覆盖。要改文章或外观，应改源码，再重新构建。

**锁文件** `pnpm-lock.yaml` 记录依赖及其相互关系的实际版本，让另一台电脑和服务器尽量安装相同依赖。只交 `package.json`、丢掉锁文件，可能导致“我电脑上正常，服务器失败”。

通常进入 Git：文章、用到的图片、个人代码、项目配置、`package.json`、`pnpm-lock.yaml`、长期文档。不进入 Git：依赖、生成网站、缓存、日志、密码和令牌。

当前 `.gitignore` 忽略了 `dist/`、`.astro/`、`node_modules/`、`.vercel`、`.env`、`.env.production` 和部分日志、其他包管理器锁文件。**它没有承诺忽略所有 `.env.*` 文件**。新增环境文件要检查规则；点开头不代表保密。已被 Git 跟踪的文件，也不会因后来增加忽略规则自动移除。

## 终端入门：先知道自己站在哪里

### 打开 PowerShell，确认位置

可以从 VS Code 的“终端 → 新建终端”打开，也可以从 Windows 开始菜单打开 PowerShell。Windows Terminal 是容纳 PowerShell 的窗口程序，不是另一套必须学习的命令。

在 PowerShell 输入：

```powershell
Set-Location 'C:\code\blog-astro'
Get-Location
Get-ChildItem
Test-Path .\package.json
```

依次是：切换目录、显示位置、列文件、确认项目文件存在。成功时路径为 `C:\code\blog-astro`，最后返回 `True`。英文单引号括住整条路径，路径有空格也不容易拆错。这里不使用 CMD 的 `cd /d`。

每行命令后按 Enter。输出不是下一条命令，不要把错误堆栈粘贴回去。涉及删除时，先确认具体文件和后果。

### 服务为什么一直占着终端

`dev` 是持续工作的程序：它等浏览器请求，也盯着文件变化，所以不会立即退出。服务已就绪、终端仍停在那里是正常现象。

- 停止服务：选中该终端，按 `Ctrl+C`。
- 边预览边运行 Git：新建第二个 PowerShell，再确认项目目录。
- 修改正文：通常保存即可，开发服务器会更新。
- 修改配置、环境变量或依赖：必要时停止重启。在另一个终端设置环境变量，不影响已运行的旧进程。

### 工具和依赖不是同一回事

在 PowerShell、项目目录执行只读检查：

```powershell
node --version
git --version
corepack pnpm --version
```

本次 Node.js 是 `v22.19.0`，包管理器是 `9.14.4`。Corepack 帮助调用项目指定包管理器；本机已具备它。另一台电脑若连 `node`、`git`、`corepack` 都找不到，应先按各自官方安装说明安装工具，并重开终端，让新安装目录进入命令搜索路径。不同 Node 安装方式不一定附带 Corepack。

“找不到命令”通常意味着工具未安装、命令搜索路径未更新，或拼错名称。“找不到 `package.json`”常常是站错目录：还在用户主目录，或只进入了 `src`。先看 `Get-Location`，再检查文件。

### 第一次克隆与日常写作不同

**克隆**是从远程取得项目及已有 Git 历史。本机已有项目，不要在里面再克隆一层。换电脑时，从 GitHub 复制**自己的仓库**地址，在存放项目的父目录执行。

下面仅适用于新电脑且目标文件夹不存在。先将中文占位字符串替换为自己的真实 HTTPS 仓库地址，**不能原样执行**：

```powershell
Set-Location 'C:\code'
git clone '替换为自己的仓库HTTPS地址' blog-astro
Set-Location 'C:\code\blog-astro'
corepack pnpm install
corepack pnpm dev
```

成功后得到项目文件、Git 历史和依赖。下载失败时保留错误信息，先区分网络与版本问题，不要反复克隆覆盖写作目录。日常写作只需进目录、启动服务、编辑保存。

## 本地启动与两种预览

### 本项目确实提供哪些命令

命令来自根目录 `package.json` 的 `scripts`，都在 PowerShell 的项目根目录运行。

| 命令 | 作用与成功标志 |
| --- | --- |
| `corepack pnpm install` | 安装或同步依赖；完成且无致命错误 |
| `corepack pnpm dev` | 开发预览；出现 `Local` 地址 |
| `corepack pnpm start` | 与 `dev` 相同 |
| `corepack pnpm build` | 生成网页和搜索索引；两步都完成 |
| `corepack pnpm preview` | 提供已有 `dist/` 的本机预览 |
| `corepack pnpm check` | Astro 检查；不会发布网站 |
| `corepack pnpm new-post 文件名` | 在文章目录创建 `.md` 文件 |

`build` 的真实内容是 `astro build && pagefind --site dist`。它在脚本内部串联两步；本文给 PowerShell 的命令逐行写，兼容不支持 `&&` 的 Windows PowerShell 5.1。直接用 `corepack pnpm astro build` 会跳过 Pagefind，不能代替完整发布构建。

项目还提供 `astro`、`type-check`、`format`、`lint`。当前 `format` 和 `lint` 都带 `--write`，**会改写文件**，不是只读检查。不要为了消除提示随手全目录格式化。

### 开发预览与构建预览有什么区别

| 对比项 | `dev` | `build` 后的 `preview` |
| --- | --- | --- |
| 内容来源 | 当前源码 | 上一次生成的 `dist/` |
| 保存后 | 通常自动更新 | 必须重新构建 |
| 草稿 | 显示，可直接访问 | 不生成文章网页 |
| 搜索 | 固定假结果 | 真实 Pagefind 索引 |
| 用途 | 边写边看 | 检查即将部署的成品 |

`localhost`、`127.0.0.1` 都指当前电脑，不是公网博客域名。发给别人后，对方访问的是自己的电脑；手机上的 `localhost` 也不是你的电脑。真机局域网访问另需配置监听地址和防火墙，普通写作不必开放网络访问。

默认端口通常为 `4321`。若被占用，日志会提示，服务可能选下一个端口。以本次 `Local` 完整地址为准，别一直看旧端口。开发和构建预览同时开着时尤其要留意。

### 当前环境遇到遥测问题怎么办

遥测是工具收集使用统计的机制。如果受限环境不允许 Astro 写入用户目录中的遥测设置，在**启动 Astro 的那个 PowerShell**执行：

```powershell
$env:ASTRO_TELEMETRY_DISABLED = '1'
corepack pnpm dev
```

构建也可在此环境运行。设置随终端退出消失，新终端需要时再设，不必改源码。不要混用 Bash 的 `export` 或 CMD 的 `set`。它只处理遥测相关问题，不能修复缺图、YAML 或所有权限错误。

## 创建一篇文章：先弄懂文件开头

### 新建文件与最小模板

在 VS Code 左侧展开 `src/content/posts`，右键“新建文件”，输入 `my-first-post.md`。确认后缀是 `.md`，不要因 Windows 隐藏扩展名而创建成 `.md.txt`。文件名可换成自己的简短英文主题。

下面是**完整文件内容**，复制进新文件；日期换成自己实际写作的日期：

```markdown
---
title: '我的第一篇文章'
published: 2026-10-25
draft: true
---

这是第一段正文。

## 今天想记录什么

把想说的话写在这里。
```

两条 `---` 之间称为 **frontmatter**，可以理解为“文章资料卡”；它使用 **YAML** 这种按“字段名：值”写设置的格式。第二条 `---` 之后才是正文。

也可在项目 PowerShell 执行：

```powershell
corepack pnpm new-post my-first-post
```

脚本会生成 `src/content/posts/my-first-post.md`，同名文件已存在时拒绝覆盖。**当前脚本默认写 `draft: false`**，创建后立即在编辑器改为 `true`，再开始写作。脚本接受 `.mdx` 后缀，不代表已经安装 MDX 支持；日常请选择 `.md`。

### 常用资料卡模板

下列内容放在文章最上面，不是终端命令。`updated` 初次写作可以省略。

```yaml
---
title: '我的第一篇文章：开始记录'
published: 2026-10-25
draft: true
description: '用一两句话介绍文章内容。'
image: ''
tags: ['写作', '生活']
category: '日常记录'
lang: 'zh_CN'
---
```

**Schema** 是“允许哪些字段、每项必须是什么类型”的规则，定义在 `src/content/config.ts`。

| 字段 | 类型与要求 | 用途与默认值 |
| --- | --- | --- |
| `title` | 必填，字符串 | 标题，无默认值 |
| `published` | 必填，日期 | 显示、排序、元数据，无默认值 |
| `updated` | 可选，日期 | 更新日期；省略或等于首次日期时不显示独立更新标记 |
| `draft` | 可选，布尔值 | `true` 或 `false`，默认 `false` |
| `description` | 可选，字符串 | 摘要，默认 `''` |
| `image` | 可选，字符串 | 封面路径，默认 `''` 即无封面 |
| `tags` | 可选，字符串数组 | 多个标签，默认 `[]` |
| `category` | 可选，字符串或 `null` | 单个分类，默认 `''`，空值归未分类 |
| `lang` | 可选，字符串 | 默认 `''` 时沿用站点语言 |

字符串就是一段文字；布尔值表示是/否；数组是一组值。分类像主要书架，一篇文章填一个；标签像贴纸，可以多个。不要写 `category: ['技术', '生活']`，当前不接受分类数组。`tags` 也不能写成一段没有方括号的逗号分隔字符串。

`prevTitle`、`prevSlug`、`nextTitle`、`nextSlug` 是程序根据排序填写的内部字段，用于上一篇、下一篇。它们默认空字符串，日常不手动填写。

### YAML 最容易写错的细节

- 用英文半角冒号，后留空格，如 `title: '标题'`。
- 引号用英文单引号或双引号，不用中文弯引号充当语法。标题含冒号加空格、`#` 等时尤其应加引号。
- 日期建议不加引号，按 `2026-10-25` 写；当前要求日期类型。`updated` 不用时省略，不写 `updated: ''`。
- `draft: true` 是布尔值，`draft: 'true'` 是字符串，两者不同。
- `image: ''` 是空字符串；`image:` 是空值，当前字段不接受后者。
- `category: null` 被允许，日常用 `category: ''` 更统一。
- 缩进用空格，不用 Tab。数组也能分行，同层连字符对齐：

```yaml
tags:
  - 'Git'
  - 'Markdown'
```

空字符串、空数组、空值不是一回事。校验失败时先看报错中的文件和字段，再对照规则修改，不要删除整张资料卡。

### 文件名、目录名和网址

**URL** 是网页地址；**slug** 是程序用来拼接文章网址的路径片段。当前路由使用 `entry.slug`，前面加 `/posts/`，末尾加斜杠。标题可以中文，网址不必照搬标题。

| 源文件（从文章目录算起） | 当前规则下的网址路径 |
| --- | --- |
| `blog-handbook.md` | `/posts/blog-handbook/` |
| `my-first-post.md` | `/posts/my-first-post/` |
| `guide/index.md` | `/posts/guide/` |
| `notes/day-one.md` | `/posts/notes/day-one/` |

目录式文章末尾的 `index` 会去掉。原主题的 `guide/index.md` 曾用于验证这条规则；自带示例文章现已删除，表中的 `guide` 路径仅保留为写法示范。目录式文章适合把正文与图片收在同一文件夹，不需要另写 HTML 首页。不要同时建 `guide.md` 和 `guide/index.md` 争用同一网址。

修改 `title` 通常只改显示文字；改文件名或父目录可能改变链接。`guide/index.md` 移到 `guide.md` 可保持这条规则下的 slug，但图片的相对位置会变。链接改了应考虑旧链接的跳转，本项目没有自动为所有改名生成重定向。

Astro 会处理大小写、空格等字符。优先用小写英文、数字、短横线，避免依赖复杂转换，保存后实际访问确认。本文不要求额外填写自定义 `slug`。

### 草稿不是保密存储，日期也不是定时开关

`src/utils/content-utils.ts` 开发时保留所有文章，生产时只保留 `draft !== true` 的文章。文章路由、首页、分类标签使用这套筛选逻辑。

- `draft: true`：开发预览可见，正式构建不生成文章网页，也不进入本次正式搜索索引。
- `draft: false` 或省略：参加正式构建。省略不表示“还没发布”。
- 草稿源码仍是普通文件，提交到公开仓库后别人能看到；不适合存密码和私人资料。

`published` 是日期显示、排序和元数据，**没有按今天过滤未来日期**。把它改成明年不能定时发布；只要不是草稿，下次构建仍会包含它。

修改正文通常保留首次 `published`。实质增补或纠错时增加 `updated`，填写真实修订日期。改一处标点不必重写首次发布日期。

## Git 零基础：跟着一篇新文章走

### 五个词，串成一条路

**工作区**就是你眼前的项目文件；**暂存区**像准备装订的一叠稿纸，用来挑选这次提交包含什么；**本地提交**是把这叠稿纸正式记入版本历史。**分支**是一条有名字的提交路线，方便不同工作并行。**远程仓库**是另一处保存历史的仓库，常托管在 GitHub。

流程是：编辑文件 → 检查工作区 → 选择改动放入暂存区 → 再检查 → 本地提交 → 按需推送。暂存以后继续修改文件，会出现“已暂存旧内容”和“尚未暂存新内容”并存，需要重新检查。

### 先看，再添加

以下命令在项目 PowerShell 运行：

```powershell
git status
git diff
```

`status` 是状态总览，会告诉你当前分支、哪些已修改、哪些新建但未跟踪、哪些已暂存。**未跟踪**意味着 Git 还没有把新文件纳入版本管理。普通 `git diff` 主要比较已跟踪文件的工作区与暂存区，**不会展示未跟踪新文件的全部正文**。看到空白差异不代表新文章不存在。

查看新文章时，在 VS Code 打开它，或执行：

```powershell
Get-Content -LiteralPath 'src/content/posts/my-first-post.md' -Encoding UTF8
```

确认它就是本次要保存的内容后，再执行：

```powershell
git add -- src/content/posts/my-first-post.md
git diff --cached --stat
git diff --cached
git status
```

这里的文件名要换成实际写的文章；本篇是 `src/content/posts/blog-handbook.md`。配图也要逐一添加实际路径，不要漏掉。`--cached` 显示将要提交的暂存内容。确认正文、日期和图片正确、没有别人的未完成修改或私密信息后，才能提交。

不要默认 `git add .`：点号会把当前目录下符合条件的其他改动也一起加入，容易夹带不相关文件。`git add -- 文件路径` 的 `--` 用来明确后面是路径。

### 保存一份有说明的本地版本

以下是你以后主动保存文章版本时的操作；本手册的编写过程没有自动执行提交。

```powershell
git commit -m 'docs: 添加第一篇文章'
git log -5 --oneline
git status
```

提交说明可以写中文，尽量说清改了什么。`git log` 显示历史；每条前面的短字符串是提交编号，用来定位版本。命令返回成功后，已提交内容就保存在本地历史里了，**此时没有推送也没有部署**。

若 Git 打开分页阅读界面，按 `q` 退出；不要以为终端卡死。提交报身份未配置时，看故障章节，不要把教程里的姓名邮箱当成自己的。

### 远程和分支：先确认目标，别只背名字

运行只读检查：

```powershell
git branch --show-current
git branch -vv
git remote -v
```

第一条显示当前分支，第二条还能看到分支的**跟踪关系**，也就是本地分支默认对应哪条远程分支。当前检查结果是：`my-blog` 没有显示跟踪目标；`main` 跟踪 `upstream/main`。

`origin`、`upstream` 只是远程的名字。习惯上前者常指自己的仓库，后者常指原项目，但**名称不保证所有权、写入权限或用途**。`git remote -v` 的 `(push)` 表示配置的推送地址，也不是已获写权限的证明。

本项目现在只有 `upstream`，实际地址指向官方 Fuwari。个人博客不应直接推送到它。要上线，后续还需要：创建或确认自己的仓库、把它配置为一个经过核对的远程、确认登录权限、选定发布分支、连接托管平台。

这里不提供当前可直接复制执行的 `git push` 目标，因为正确的个人仓库尚未配置。将来确认 `origin` 确实是自己的仓库、目标分支正确后，再按该流程推送；不要把“通常叫 origin”变成未经检查的假设。

## Markdown 完整入门

下面的“源码”都放进 `.md` 正文，不是 PowerShell 命令。代码框里展示写法，框外说明浏览器会显示什么。

### 标题：用结构表达层次

源码：

```markdown
## 一个大章节

### 这个章节里的小节

#### 小节内的进一步说明
```

`#` 后要有空格，井号越多层级越深，最多六级。主题已经显示 frontmatter 中的文章标题，正文一般从 `##` 开始。不要为了字大直接写一个新的一级标题，也不要从二级跳到六级。成功后标题会按层次显示，并被自动目录读取。代码框里的示例标题不会进入正文目录。

### 段落、单换行和明确换行

源码：

```markdown
这是第一段。

这是第二段。
```

空一行表示分段，渲染后两段有段落间距。连续多空行通常不会产生同样多的空白，不用它们控制版面。

下面是普通单换行的源码和实际示例：

```markdown
窗边有一盏灯。
我把今天写下来。
```

窗边有一盏灯。
我把今天写下来。

当前渲染器把这两行放进**同一个段落**，没有自动插入 `<br>`。浏览器会合并这种普通空白，是否因屏幕宽度换行是另一回事；它不是“源码每行等于网页一行”。写小说时分段用空行，写诗词要保留分行可明确换行。

可以在行尾加两个半角空格，但空格不易看见、也可能被编辑器清理。更直观的 HTML 换行写法如下：

```markdown
窗边有一盏灯。<br>
我把今天写下来。
```

窗边有一盏灯。<br>
我把今天写下来。

效果是同一段里明确分两行。这里的 `<br>` 是 HTML 换行标签。长诗也可以用后面介绍的 `white-space: pre-line`，但普通文章不要通篇强制断行。

### 加粗、斜体和删除线

```markdown
这是 **重要内容**，这是 *轻微强调*，这是 ~~已不再适用的文字~~。
```

这是 **重要内容**，这是 *轻微强调*，这是 ~~已不再适用的文字~~。

它们表达重要性、语气或删改，不是选择任意字号和字体。中文斜体是否好看取决于字体，后面单独说明。星号要成对，避免只开不关。

### 分隔线

```markdown
前一部分结束。

---

后一部分开始。
```

正文中的独立 `---` 可以形成横向分隔线。上下留空行，避免它被解释成前一行的标题下划线；文件最顶部的两条 `---` 则是资料卡边界。

### 有序、无序、嵌套和任务列表

```markdown
- 准备正文
- 检查配图
  - 图片是否存在
  - 文件名大小写是否相同

1. 保存文件
2. 打开预览
3. 核对页面

- [x] 已保存
- [ ] 还没有公开
```

效果：无序列表显示项目符号，有序列表显示编号，缩进让子项归属于上一项。任务列表在当前配置中支持，显示复选框：

- [x] 已保存
- [ ] 还没有公开

它是文章里的状态展示，不是会替你保存进度的待办应用。更改状态要改源码的 `x` 或空格。列表内容较复杂时用空行分隔，代码块要缩进到对应列表项之内。

### 链接、站内链接和锚点

```markdown
[查看 Astro 文档](https://docs.astro.build/zh-cn/)

[关于本站](/about/)

[这份使用手册](/posts/blog-handbook/)

[跳到示例位置](#handbook-anchor-example)

<span id='handbook-anchor-example'>这是示例目标。</span>
```

方括号是可读文字，圆括号是地址。`https://` 开头是完整外部地址，`/about/` 是从本站根目录算起的路径；当前 `base` 为 `/`，这些站内路径适用。以后改成子目录部署，需要重新检查手写链接，普通 Markdown 不会替所有链接调用项目的 `url()` 辅助函数。

**锚点**像书签，用 `#` 跳到同页某个位置。上述手动 `id` 只演示单个目标，不用来维护文章目录：

[跳到示例位置](#handbook-anchor-example)

<span id='handbook-anchor-example'>这是示例目标。</span>

本项目会自动为标题加锚点。真正引用标题时，可在预览中点击标题旁的 `#` 复制地址，不要猜复杂中文标题的转换结果；改标题后锚点也可能变化。

### 图片和替代文字

```markdown
![项目自带的示例头像](../../assets/images/demo-avatar.png)
```

![项目自带的示例头像](../../assets/images/demo-avatar.png)

这是本篇所在目录可以实际解析的现有图片，不是给本文虚构的新封面。`!` 表示图片；方括号是**替代文字**，帮助无法看图的人理解内容，也会在图片加载失败时提供说明。它不一定显示成图下注释；需要图注就在下一段写说明。

### 引用

```markdown
> 先看改动，再决定是否提交。
> 这是同一引用中的下一行。
```

效果是一块带引用样式的文字，其中普通单换行仍不自动变硬换行。引用别人的原话应写明来源；引用样式本身不代表内容有权威性。

### 表格及其局限

```markdown
| 操作 | 是否立即上线 |
| --- | --- |
| 保存 | 否 |
| 本地预览 | 否 |
```

效果是两列表格。第二行不能省略。对齐可用 `:---`、`:---:`、`---:` 表示左、中、右对齐。当前支持这类表格，但标准 Markdown 表格不适合合并单元格、多段文字或复杂布局。

手机上优先用少列、短内容。超长路径和一大段代码放到表格外的代码块；不要用一张十几列表格迫使读者横向找字。单元格内需要竖线时用 `\|` 转义。

### 行内代码、代码块和语言标记

源码中的单反引号用于短命令或文件名：

```markdown
编辑 `src/config.ts` 后，再运行 `corepack pnpm dev`。
```

效果是句子中的等宽代码片段。多行内容用独立代码块。下面外层用四个反引号，这样可以安全展示内层的三个反引号，不会把教程提前截断：

````markdown
```powershell
Get-Location
git status
```
````

效果是带 PowerShell 高亮的代码框。`powershell`、`markdown`、`yaml`、`javascript`、`html`、`css`、`text` 都是语言标记，供高亮器判断内容；它们不属于需要复制执行的代码。展示普通文字用 `text`。代码块只展示代码，不会自动执行命令。

如果要在行内代码里出现反引号，可用两个反引号包围：

```markdown
``这里有一个 ` 符号``
```

闭合围栏要与开头匹配。长文突然全部变成代码，常常就是少了一行闭合围栏。

### 特殊符号转义与原始 HTML

反斜杠让特殊符号按普通文字显示：

```markdown
\*这不是斜体\*

\# 这不是标题

显示标签名称：&lt;span&gt;
```

效果分别是带字面星号的文字、字面井号和 `<span>` 标签名。讲代码时优先用代码块，避免为每个符号单独转义。

当前 Markdown 允许原始 HTML。比如：

```html
<p>这里有 <strong>HTML 加粗</strong> 和 <br>明确换行。</p>
```

放在正文时会按 HTML 渲染；放在代码框里只是展示源码。原始 HTML 容器中不要想当然地认为 `**加粗**` 一定还会解析，最稳妥是容器内部使用 HTML 标签。闭合标签、属性引号要配对；不要复制来路不明的脚本。依赖列表里有 `sanitize-html` 不表示所有文章 HTML 都经过统一安全过滤。

## 字体、字号、颜色与排版

### 先分清你到底想改什么

| 概念 | 改变什么 | 例子 |
| --- | --- | --- |
| 文字强调 | 表达重要性或语气 | Markdown 的加粗、斜体 |
| 字号 | 字的大小 | CSS 的 `font-size` |
| 字体家族 | 字形来自哪一种字体 | `font-family` |
| 字体字重 | 同一字体的粗细 | `font-weight`，如 400、700 |
| 行高 | 一行文字占据的垂直空间 | `line-height` |
| 文字颜色 | 字的颜色 | `color` |
| 局部样式 | 只影响一个片段或指定元素 | 一段诗的行高 |
| 全站样式 | 影响很多页面的共同规则 | 整站默认字体 |

**CSS** 是描述网页外观的规则。普通 Markdown 没有通用的“设置为某字体、18 号字、红色”的语法；某款笔记软件的专属标记不一定能搬到博客。当前项目允许 HTML，所以可以对小范围内容用 HTML 加 CSS。

### 当前能用的局部排版示例

下面是**写入 Markdown 正文的文件内容**。`style` 属性里的规则只作用于这个段落：

```html
<p style='font-size: 1.125rem; line-height: 1.9; font-weight: 600; color: var(--primary);'>
请先预览，再决定是否公开。
</p>
```

<p style='font-size: 1.125rem; line-height: 1.9; font-weight: 600; color: var(--primary);'>
请先预览，再决定是否公开。
</p>

`rem` 按网页根字号计算，相比固定像素更容易随整体字号缩放；`line-height: 1.9` 让行高随字号变化；600 是偏粗字重，不保证每种字体都有独立的 600 字形。`var(--primary)` 使用当前主题色变量，能随主题变化，但自选主题色仍要检查可读性。

想保留一小段诗的源码换行，可以这样写。这里使用自写示例，不引用他人诗作：

```html
<p style='white-space: pre-line; line-height: 2; font-family: serif;'>窗边有一盏灯。
我把今天写下来。</p>
```

<p style='white-space: pre-line; line-height: 2; font-family: serif;'>窗边有一盏灯。
我把今天写下来。</p>

`white-space: pre-line` 保留换行、合并多余空格；这是显式 CSS 的结果，不是普通 Markdown 单换行的新规则。`serif` 请求系统提供衬线字体，实际中文字体取决于操作系统。

### 长期维护优先用有含义的类名

**类名**是给一类元素贴的样式标签。只有一段时，行内 `style` 直观；重复很多篇时，复制一长串样式难统一修改。可以以后在 `src/styles/markdown.css` 增加有明确用途的规则，例如：

```css
.custom-md .reading-note {
    font-size: 1.125rem;
    line-height: 1.9;
    color: var(--tw-prose-body);
}

.custom-md .poem-lines {
    white-space: pre-line;
    line-height: 2;
}
```

再在文章中使用：

```html
<p class='reading-note'>这是一段需要舒展阅读的文字。</p>
```

**上面的类名是未来改样式的示范，本轮没有把它加入全站 CSS。** 直接复制类名而不添加规则，不会获得新效果。前面两个行内样式示例则已可直接使用。用 `.custom-md` 限制范围，避免无意改到导航、友链或其他页面。

### 全站字体真正应该改哪里

当前正文默认字体列表在根目录 `tailwind.config.cjs` 的 `theme.extend.fontFamily.sans`；Roboto 的 400、500、700 字重由 `src/layouts/Layout.astro` 导入。正文的 Markdown 外观主要在 `src/styles/markdown.css`、`src/styles/markdown-extend.styl`；代码字体由 `src/components/misc/Markdown.astro` 导入 JetBrains Mono，并在 Markdown 样式、`src/styles/expressive-code.css` 与 `astro.config.mjs` 的代码样式配置中指定。

也就是说，正文默认字体、行内代码字体、代码框字体并不是同一个开关。普通改文章不用碰这些文件。

如果将来只想调整正文默认字体，可以在 `tailwind.config.cjs` 中**替换已有的 `sans` 属性值**，不要把下面片段当完整配置覆盖整个文件：

```javascript
sans: ['Roboto', 'Microsoft YaHei', 'PingFang SC', 'Noto Sans CJK SC', ...defaultTheme.fontFamily.sans],
```

**后备字体列表**会从前往后尝试：一种字体没有某个字，就找后面的字体。例如 Roboto 主要覆盖拉丁文字，中文通常需要后备字体。列出名称并不会自动下载字体；电脑上没有就继续找下一项。当前原配置把通用 `sans-serif` 放得较早，后面的具体字体未必按你设想的顺序被选中。若要指定中文字体优先级，应在通用后备之前明确列出。

本文只说明位置与思路，**没有修改全站字体或设计**。真正修改后应重启开发服务，并检查正文、加粗、代码、深浅色和手机效果。

### 系统字体、在线字体和本地字体

- **系统字体**已经在访客设备中，不必下载，速度快，但 Windows、macOS、手机可能显示不同字形。
- **在线字体**由其他服务器提供，需要额外网络请求；可用性、隐私、跨域和加载时间都要考虑。
- **本地托管字体**把有使用权限的字体文件放进项目，通过 `@font-face` 等方式提供。当前 Fontsource 字体是依赖中的字体资源，构建后由站点提供，不等于访客必须能连到 Google Fonts。

中文字体包含大量字形，文件可能很大。只用需要的字重，考虑合法的子集化与 WOFF2 等适合网页的格式，测试慢网络。下载到文件不代表拥有再分发许可，要核实字体授权。不要为了“统一外观”一次加载好几套完整中文字库。

中文不一定有专门设计的斜体，浏览器可能机械倾斜，效果未必自然。重要内容通常加粗或用提示块更稳妥。字重和字号也不是同一件事：把字变大不会自动表达更强语义。

颜色尽量沿用主题变量，例如正文使用 `var(--tw-prose-body)`。固定黑字放在深色背景、固定白字放在浅色背景都可能看不清；局部背景色也要一起考虑。不要只用红绿区分重要状态，还应写出文字。

### 不靠空格和“大字”代替结构

标题用真正的 `##`、`###`，不要把普通段落改大假装标题，否则目录和阅读辅助工具不能正确识别。不要用全角空格、连续空行对齐文字，手机宽度变化后很容易散架。段落、列表、少列表格通常更可靠。

**MDX** 是在 Markdown 中进一步使用组件和程序表达式的格式。当前没有配置 `@astrojs/mdx` 集成，所以不把改后缀当成已经接入。普通文章完全可以继续用 `.md`；为了偶尔调字号，无需改用 MDX。

## 图片、封面、头像和横幅

### 四种图片，四个入口

| 用途 | 设置位置 | 当前说明 |
| --- | --- | --- |
| 正文图片 | 文章中的 `![说明](路径)` | 可以多张，跟着正文出现 |
| 文章封面 | frontmatter 的 `image` | 文章卡片和文章上方使用 |
| 个人头像 | `src/config.ts` 的 `profileConfig.avatar` | 当前是项目自带示例头像 |
| 站点横幅 | `siteConfig.banner` | 当前 `enable: false` |

横幅是站点背景区域，封面是一篇文章的配图。当前布局明确使用站点横幅配置，不自动把文章封面当作横幅。本文封面为 `image: ''`，没有为了填字段而虚构素材。

### 放在 src 还是 public

`src` 下的图片会参与构建处理，Markdown 的相对图片可被 Astro 解析、优化，输出路径可能带生成名称。`public` 下的文件通常按原路径复制，适合固定网址的静态资源，但不会因为放进去就自动完成同样的图片优化。

本篇的相对路径例子：

```markdown
![项目示例头像](../../assets/images/demo-avatar.png)
```

从 `src/content/posts/blog-handbook.md` 所在目录出发，两个 `..` 回到 `src`，再进入 `assets/images`。如果把文章改成目录式的 `blog-handbook/index.md`，这一相对路径需要重新计算。

已有静态图片例子：

```markdown
![现有友链条目的头像示例](/images/wxz.jpg)
```

![现有友链条目的头像示例](/images/wxz.jpg)

这里引用现有友链头像只为示范根路径，不表示它属于文章作者，也不建议拿朋友头像作个人头像。它在磁盘上是 `public/images/wxz.jpg`，网址中不写 `/public/`。实际新文章请使用有权使用的素材。

相对路径是“从当前文件所在位置出发”，根路径是“从网站根目录出发”。`C:\Users\...\photo.jpg` 是你电脑的磁盘位置，读者电脑没有这个文件，不能作为公开图片网址。网页路径统一用 `/`，不使用 Windows 反斜杠。

### 符合当前 ImageWrapper 的封面写法

`ImageWrapper.astro` 处理封面、头像、横幅；正文 Markdown 图片由 Astro 的 Markdown 图片流程处理，二者不要混为同一组件。

当前 ImageWrapper 根据路径前缀判断来源：`/` 开头按 `public` 根路径；`http` 或 `https` 开头按远程 URL；其他普通相对路径按调用组件时的基准目录查找。`data:` 也被分到非本地来源，但日常不建议把大段图片编码塞进文章。

对**文章封面**，基准目录是文章文件所在目录。例如将来创建 `guide/index.md`，并在同目录准备自己的 `cover.jpeg` 后，可以写：

```yaml
image: './cover.jpeg'
```

它对应 `src/content/posts/guide/cover.jpeg`；原主题的这组示例文件现已删除，不能在没有图片时照抄此路径。如果本篇确实想测试已有头像作为封面，路径语法上可以用下列之一；**本篇实际仍保留无封面**：

```yaml
image: '../../assets/images/demo-avatar.png'
```

或者引用已有 public 图片：

```yaml
image: '/images/wxz.jpg'
```

只选一条，不能重复写两个 `image`。不要写成 `/src/assets/...` 或 `/public/images/...`。

对**站点头像和横幅**，`src/config.ts` 中当前有效格式是 `assets/images/demo-avatar.png` 和 `assets/images/demo-banner.png`，相对 `src/`。同一个相对字符串放在封面资料卡和站点配置里，基准位置不一定相同。

当前 ImageWrapper 仍使用较宽的 `import.meta.glob`，本地图片未找到时会打印错误，随后调用缺失导入还可能使页面失败；没有可靠的“随便写路径也会自动兜底”。看到 `Image file not found`，先查路径、大小写和文件是否存在。本轮未改这个组件。

### 名称、大小、授权与引用检查

Windows 文件系统常常不区分文件名大小写，线上 Linux 通常区分。`Cover.JPG` 和 `cover.jpg` 不应混用。项目里有 `.JPG`、`.WEBP` 这类大写后缀，引用时照真实文件名写。

中文或带空格的文件名并非一律不能用，但 URL 可能出现百分号编码，复制、大小写和跨平台处理更容易出错。长期维护建议小写英文短横线，例如 `writing-desk.webp`；改名后同步所有引用。

用合适尺寸和压缩，别把几十 MB 原图当作小头像。照片可考虑 JPEG、WebP、AVIF，透明图按需求选 PNG 或其他支持透明的格式；兼顾浏览器与构建工具支持。外链图可能失效或被防盗链，重要图片在有授权前提下自己托管更稳定。

正文图片写清楚替代文字，必要时附来源。原始 HTML 图片设置合适的 `width`、`height` 能帮助页面提前预留空间；CSS 再用 `max-width: 100%` 保持响应式。不要仅靠把显示宽度缩小来代替压缩文件。

删除图片前，用 VS Code 的 `Ctrl+Shift+F` 搜索文件名，再搜索完整路径。检查文章、资料卡、`src/config.ts`、友链数据和 CSS，也注意可能由程序拼接路径。搜索不到不等于绝对没用；动态引用和站外旧链接还需判断。先在 Git 中保存有用版本、核实预览后再删，别清空整个图片目录。

当前页面还接入 PhotoSwipe：正文和封面图片可点开查看大图。能否成功显示仍取决于图片资源可访问，不是一个自动上传或修图服务。

## 一篇文章从写作到上线

### 先完成本机的写作与验收

1. **新建草稿。** 在 VS Code 的 `src/content/posts/` 创建文章，填写标题、实际日期，明确设 `draft: true`。没有封面就省略 `image` 或写 `image: ''`。
2. **本地预览。** 在项目 PowerShell 运行 `corepack pnpm dev`，按输出地址打开文章。核对正文、图片、链接、代码块、自动目录，缩窄浏览器查看手机宽度；也检查深浅色。
3. **决定公开。** 内容确认后，在编辑器把 `draft` 改为 `false` 并保存。首次发布日期按实际决定填写，后续更新用 `updated`。本篇交付时仍保留 `true`，由你预览后决定是否公开。
4. **构建。** 可先在开发终端按 `Ctrl+C`，再执行下列命令。构建成功后才继续下一条：

   ```powershell
   corepack pnpm build
   corepack pnpm preview
   ```

5. **构建预览。** 浏览器打开预览终端显示的地址。检查首页出现文章、文章链接正常、图片正常，搜索能找到标题和正文。如果这里仍是草稿，找不到是预期行为；不要把草稿 404 当成路由坏了。
6. **检查改动。** 新开第二个项目 PowerShell，执行 `git status` 和 `git diff`。新文件要在编辑器中读；依赖锁文件或配置有变化时确认是否本来就打算修改。
7. **选择并复查暂存内容。** 用 `git add -- 实际路径` 逐个选择文章和配图，再看 `git diff --cached`。这处中文是解释用占位，不是要原样执行的路径。
8. **提交。** 确认无误后执行适合这次内容的 `git commit -m '说明本次改动'`，用 `git log -5 --oneline` 和 `git status` 查看结果。提交是你的操作决定，不会由本文或写作助手自动完成。

- `.github/workflows/build.yml` 对 `main` 的推送和拉取请求做检查与构建；它没有上传部署产物或发布网站的步骤。当前构建工作流调用 `pnpm astro build`，也没有运行完整脚本中的 Pagefind。
- `.github/workflows/biome.yml` 是代码质量检查，不是部署流程。
- `astro.config.mjs` 的 `site` 写了域名，但域名配置不证明 DNS、HTTPS 和托管已生效。

后续配置时应按这个顺序完成，而不是直接向现有 `upstream` 推送：

1. 在 GitHub 确认你拥有的个人博客仓库，取得其真实地址。选择公开还是私有时考虑文章源码和草稿的可见性。
2. 在本地配置个人远程并核对 `git remote -v`；名字可以叫 `origin`，关键是地址和权限。保留官方 `upstream` 用作后续参考。
3. 决定使用哪个分支发布，比如继续维护当前个人分支；核对跟踪关系，随后才执行对应的推送命令。本手册不填造假的账号和目标，也不提供会误推官方仓库的命令。
4. 在选择的托管平台中连接那个仓库和分支。构建步骤使用 `corepack pnpm build`（平台已提供独立 pnpm 时可用 `pnpm build`），静态产物目录为 `dist`，项目根目录是含 `package.json` 的位置。安装步骤需要正确的 Node 与 pnpm 版本及锁文件。
5. 核对 `site`、`base` 与实际域名和访问路径一致。子目录托管要额外检查所有根路径链接、静态图片和友链头像。
6. 部署成功后，确认平台日志对应刚才的提交，再访问真正公网地址，核对标题、图片、手机排版、中文搜索、深浅色和主要页面。

服务商控制台或账户中是否另有配置，本地文件不能完全证明；本文只把能核实的仓库状态写清楚。完成配置之后，推送才可能成为自动部署的触发条件。不要只看 GitHub 文件已更新就宣布上线。

## 常见故障：先定位，不急着重装

### 终端、安装与网络问题

| 现象 | 先检查什么 | 处理方向 |
| --- | --- | --- |
| 找不到 `package.json` | `Get-Location` | 切到项目根目录 |
| 找不到 `pnpm` | `corepack pnpm --version` | 本机用已验证的 Corepack 入口 |
| 找不到 `node` 或 `git` | 工具是否已安装 | 安装正确工具后重开终端 |
| Astro 模块不存在 | `node_modules` 是否安装 | 根目录运行 `corepack pnpm install` |
| 安装超时、连接失败 | 报错域名、网络、代理设置 | 修复网络后重试，保留锁文件 |
| 遥测写入受限 | 错误路径是否为统计配置 | 在同一 PowerShell 设置前述环境变量 |

安装命令需要网络下载缺失依赖。不要因为临时网络故障删除锁文件、换包管理器，或关闭证书验证。企业网络可能需要管理员提供正确代理或证书配置；不要把代理密码或访问令牌写进文章和 Git。

PowerShell 若提示某个 `.ps1` 脚本被执行策略阻止，要区分“已安装但策略不允许”和“命令不存在”。可先检查是否有同名可信 `.cmd` 入口，例如 `corepack.cmd pnpm --version`；不要把无限制降低系统执行策略当成默认修复。

### YAML 错误、文章不出现

YAML 错误通常会带文件位置。检查半角冒号、缩进、引号、资料卡边界、日期类型，以及 `tags` 是否数组、`category` 是否字符串。注意标题中的冒号加空格，未加引号可能被当成结构。

文章不出现时按顺序查：文件是否保存到 `src/content/posts/`；后缀是否 `.md`；frontmatter 是否有效；浏览器开的是开发还是构建预览；`draft` 是否为 `true`；构建后是否重新生成了 `dist`；是否看错端口。分类或标签筛选也可能把文章隐藏。未来 `published` 不是当前项目的隐藏原因。

### 图片不显示、排版突然错乱

图片问题先对照真实文件名与路径：相对路径基准、`public` 根路径、大写后缀、是否把 `C:\...` 磁盘地址写进网页、外链是否可访问。封面错误还可能使 ImageWrapper 报错。用浏览器新标签单独打开 public 图片地址，确认是不是 404；`src` 图片经过处理后的输出地址要从实际页面查看。

正文后半篇变成代码，先检查反引号围栏是否配对、展示围栏时外层是否更长、列表内缩进是否一致。提示块检查冒号结尾；原始 HTML 检查闭合标签。普通单换行不分行是默认渲染规则，参见 Markdown 章节，不是字符丢失。

### 构建失败、预览没更新

构建失败先找**最早的具体错误**，而不是只看最后一句“命令失败”。按其中的文件、字段或图片路径定位。警告与失败不同；成功应以退出状态及 Astro、Pagefind 两步是否完成判断。

浏览器兼容数据过旧等维护提示，不等于必须立刻升级所有依赖。记录提示，在有备份和检查计划时单独处理。

改完没变化：先 `Ctrl+S`，确认看的是正确文件、正确端口；开发服务是否仍在运行；生产预览是否忘了重新构建。当前还有页面切换缓存，必要时完整刷新当前地址；配置改动可停服务后重启。不要先删除全部源码缓存和依赖。

### Git 提交身份未配置

Git 用提交姓名和邮箱标记作者，这不同于 GitHub 登录凭据。先在项目 PowerShell 看：

```powershell
git config --get user.name
git config --get user.email
```

没有输出时，使用你自己希望出现在提交中的姓名和邮箱。下面是**必须替换占位内容**的示范，选择 GitHub 隐私邮箱时从自己的账户设置复制，不要猜地址：

```powershell
git config --local user.name '替换为自己的提交署名'
git config --local user.email '替换为自己的提交邮箱'
```

`--local` 只对当前仓库设置，不影响所有项目。公开仓库中的提交身份可能对外可见。身份配好不代表获得远程推送权限，推送认证是另一件事。

### 搜索搜不到

先看当前是否是 `dev`：这里显示的是组件中的固定假结果，不是真索引。然后确认是否运行完整 `build`，而不是只有 `astro build`；文章是不是草稿；是否用 `preview` 打开最新成品；浏览器是否能加载 `/pagefind/` 资源。中文搜索的实际验证和局限见下一章，不能从草稿搜不到推断中文不支持。

## 安全恢复：先弄清改动在哪一层

恢复不是一个万能按钮。先运行 `git status`，保存当前有价值的内容，必要时在项目之外复制一份备份，再针对具体文件处理。本文中的命令示例是学习材料，编写本篇时没有执行这些回滚动作。

### 未暂存的已跟踪文件修改

刚写错几行，优先用编辑器撤销或根据 `git diff` 手动改回。若确认整个文件的**未暂存改动都不要了**，才在项目 PowerShell 用：

```powershell
git restore -- src/content/posts/my-first-post.md
```

先替换为真实的已跟踪文件路径。该命令用暂存区版本覆盖工作区的未暂存改动，**会丢掉那部分内容**；若没有暂存变化，通常相当于回到上次提交的该文件版本。不要对新建未跟踪文件照抄。

### 已暂存但还没提交

如果只是选错了本次要提交的文件，撤出暂存区即可：

```powershell
git restore --staged -- src/content/posts/my-first-post.md
git status
```

这保留工作区文字，只取消暂存。已暂存的新文件取消后会重新变成未跟踪文件，这是正常结果。如果同时还有后续未暂存修改，先分别看 `git diff` 和 `git diff --cached`，不要误以为一条撤销能代替两层比较。

### 新建的未跟踪文件

Git 还没保存它，没有可供恢复的提交版本。不要把 `git restore` 当成新文件回收站。需要保留就复制备份或正常检查后纳入 Git；确实不要才在编辑器或文件资源管理器中删除那个具体文件。删除前确认不是唯一的草稿或原图。

### 已提交，以及已经推送的改动

对已提交内容，先用 `git log -5 --oneline` 找到版本，用 `git show 提交编号 -- 文件路径` 阅读历史。这里“提交编号”和“文件路径”要换成真实值。最容易理解的修复方式是：在当前文件修正问题，再创建一个新的提交，留下清楚历史。

若确实要撤销某个完整提交，Git 提供 `git revert 提交编号`，它生成一个相反方向的新提交，可能打开提交说明编辑器或出现冲突。**它会影响原提交涉及的全部文件**；只想修一段文章时不要把其他改动一起撤回。工作区有未完成内容时先处理和备份，再考虑操作。

如果已经推送，优先仍是修正提交或 `revert`，让后来的人看到明确修复。新的恢复提交还需要推送到已核对的个人远程，并按真实部署流程更新网站，线上不会仅因本机文件改回就自动恢复。

冲突表示两个版本在同一位置的修改需要人来选择，不是再执行一遍推送就能解决。保留信息、逐段理解后处理，不熟悉时停止危险操作并寻求帮助。

:::caution[不要把大范围清空当作常规修复]
`reset --hard` 可能覆盖已跟踪文件的未提交工作；`git clean` 可能删除还没进 Git 的文章和图片；强制推送会改写远程历史，影响协作者。它们不属于这份零基础日常流程。恢复前先定位具体文件，不使用一键清空来掩盖尚未理解的问题。
:::

### vanilla 不是“我的上一版博客”

**标签**是给某个提交起一个固定名称。当前 `vanilla` 指向原版基线 `6d39b0d`，之后才有个人站点配置和友链提交。它不包含最近的个人配置与友链，不能当作日常撤销目标。

需要比较原版时可只读执行：

```powershell
git show vanilla:src/config.ts
git diff vanilla -- src/config.ts
```

这只是查看，不切分支、不重置工作区。想撤销刚写错的一段，应处理具体改动，而不是“回到 vanilla”。

## 搜索与日常维护

### Pagefind 在什么时候生成索引

**索引**是搜索工具预先整理的词和页面对应关系。当前完整 `build` 先让 Astro 输出网页，再由 Pagefind 扫描 `dist/` 生成 `dist/pagefind/`。文章标题和正文有 `data-pagefind-body` 等标记，搜索不是临时读取电脑上的所有 `.md`。

`src/components/Search.svelte` 在开发模式返回固定英文假结果；即使某句提示里写着其他包管理器用法，本项目仍按 `package.json` 用 pnpm。真正测试搜索应完整构建，再开启 `preview`。

草稿被生产路由过滤，没有正式网页，自然没有搜索条目。刚编辑但未重新构建的文章，也不会自动更新旧索引。公式与带 `data-pagefind-ignore` 的元素被配置排除。

### 中文搜索怎样验证

先保证有**确实参加生产构建的中文正文**，再用标题中的“第一篇文章”和正文中的“暂存区”“替代文字”这类词测试，观察结果网址是否真指向对应文章，而非别的示例页。

若正式文章仍需保留草稿，可暂时把相同标题与中文正文制作成一篇专用测试内容，只有测试副本设为非草稿。构建后用浏览器调用真实搜索，测试完删除副本并再次构建，确保最终文章集合和索引没有残留。**绝不把“搜不到草稿”当作中文分词故障。**

本篇的实际验证结果见文末“本次验证记录”。几个关键词成功不等于所有错别字、缩写和任意子串都一定命中；搜索规则和语言处理还会受版本影响。在有证据前，不额外安装中文分词插件。

### 备份、升级与上游更新

定期检查 Git 状态并保存有说明的提交，再推送到已经核对的个人远程。尚未提交的草稿、被忽略的文件和独有原图不一定在远程备份里，需要另有副本。只留电脑上的 `.git` 不能防止硬盘损坏。私密配置用合适的安全方式备份，不公开提交。

依赖升级时先看 `package.json` 和锁文件差异，按需要逐项或小批进行，再构建、预览。`pnpm install --frozen-lockfile` 用于要求严格按现有锁文件安装的场合；依赖声明和锁文件不一致会失败，应查明原因，而非删除锁文件绕过。

Fuwari 上游更新是主题代码升级，可能影响自己的配置、友链、组件和文章行为。先保存个人工作，阅读更新说明、比较改动，在独立分支尝试并验证后再决定合并。不要直接下载新模板覆盖整个项目，也不要在不理解跟踪关系时盲目 `git pull upstream main`。

原版标签 `vanilla` 可以帮助理解差异，但不是个人内容备份。为了消除一条提示而一次升级全部依赖，反而难以知道哪项引入了问题。把“写文章”和“升级工具链”分开处理，更容易回查。
