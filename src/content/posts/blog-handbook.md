如果你刚打开这个项目，看到一堆文件和一个命令窗口，不知道应该先点哪里，这篇文章就是给你准备的。

你不需要先学会开发网站。日常写博客，先学会三件事就够了：**找到文章文件、在电脑上预览、把检查好的版本发布出去。** Git、终端和 Markdown 都会在用到时解释。

这份说明按 `C:\code\blog-astro` 的实际文件整理，更新于 **2026 年 10 月 26 日**。示例标题、日期和新文章文件名可以替换；项目目录和命令则要按自己的实际情况核对。

:::important[先记住：电脑上看得到，不等于已经上线]
保存文件，只是保存到自己的电脑。提交，是保存一个本地版本。推送，是把提交上传到 GitHub。部署，是把这个版本制作成网页并更新网站。

**推送成功以后，还要等部署成功。** 如果部署失败，网站往往继续显示上一次成功的版本，文章并没有因此被删掉。
:::

## 一、第一次使用，先走这条最短路线

### 1. 先认识三个窗口

| 在哪里 | 用来做什么 |
| --- | --- |
| VS Code 编辑器 | 打开项目，修改文字和文件 |
| PowerShell 终端 | 输入启动、检查、构建和 Git 命令 |
| 浏览器 | 看本地预览，或看已经上线的网站 |

**VS Code** 是编辑文件的软件，可以理解成适合管理整套网站文件的文本编辑器。

**终端**是输入命令的窗口。**PowerShell** 是这个窗口里理解并执行命令的程序。本文统一使用 PowerShell，不混用 CMD 的写法。

下面两种内容要分清：

- **终端命令**：复制到 PowerShell，按回车执行。
- **文件内容**：写进 VS Code 中对应的文件，按 `Ctrl+S` 保存。

不要把文章模板粘进终端，也不要把启动命令写进文章开头的资料栏。

### 2. 打开整个项目

在 VS Code 中选择“文件 → 打开文件夹”，选中：

```text
C:\code\blog-astro
```

成功后，左侧应能看到 `src`、`public` 和 `package.json`。如果只显示一个 Markdown 文件，说明你打开的是单个文件，还没有打开整个项目。

### 3. 打开终端，确认位置

在 VS Code 菜单中选择“终端 → 新建终端”，确认使用 PowerShell。输入下面两条**终端命令**，每条输完按一次回车：

```powershell
Set-Location 'C:\code\blog-astro'
Get-Location
```

看到的位置是 `C:\code\blog-astro`，再继续。

### 4. 第一次运行，安装项目需要的工具零件

网站运行时要用到的一组工具和代码叫**依赖**。第一次在这台电脑运行，先安装：

```powershell
corepack pnpm install
```

如果这台电脑已经成功安装过，而且没有更换依赖，日常写文章可以跳过这一步。不要因为改了两段文字，就每次重新安装。

### 5. 启动本地预览

```powershell
corepack pnpm dev
```

终端会给出地址。默认端口可用时，当前项目的首页是：

```text
http://localhost:4321/blogFuwari/
```

打开终端实际显示的地址。端口如果不是 `4321`，按终端的端口来。这个命令会一直运行，先保留终端，去编辑文章即可。

### 6. 新建一篇练习文章

在 VS Code 左侧展开 `src → content → posts`，右键 `posts`，选择“新建文件”，输入：

```text
my-first-note.md
```

把下面这段**文件内容**完整复制进去：

```markdown
---
title: '我的第一篇记录'
published: 2026-10-26
draft: true
---

这是我在这个博客里写下的第一段话。

## 今天想记录什么

先把想法写下来，排版可以慢慢调整。
```

标题、日期和正文是示例，请换成自己的内容。第一行和结束资料栏的 `---` 要保留。

文件必须以 `.md` 结尾，不要变成 `my-first-note.md.txt`。如果通过资源管理器创建文件，可以先打开“查看 → 显示 → 文件扩展名”，看清实际后缀。

### 7. 保存，到浏览器查看

按 `Ctrl+S`。开发首页会包含草稿；也可以直接访问：

```text
http://localhost:4321/blogFuwari/posts/my-first-note/
```

成功时，你会看到标题“我的第一篇记录”和刚写的正文。接着可以一边编辑、一边保存、一边查看效果。

:::tip[到这里，先不用急着上线]
你已经完成“在本机写文章并预览”。练习文章仍是 `draft: true`，暂时不会进入正式构建。

准备公开时，需要改为 `draft: false`，检查构建，再提交、推送，并确认部署成功。完整流程在“一篇文章从写作到上线”一章。
:::

## 二、先认识博客和工具，不用先学编程

### 1. 文件是原料，网页是成品

这个项目里保存的文章、图片、配置和页面代码，统称为**源码**，就是制作网站的原始材料。

浏览器最终展示的是 HTML 网页，以及配套的样式、脚本和图片。HTML 可以理解为浏览器认识的网页结构；样式决定外观；脚本处理搜索框等交互。

你写的 `.md` 文件需要和主题模板组合，才能变成现在这样的文章页。这个制作过程叫**构建**。

本项目构建后的文件放在 `dist`。**文章改 `src/content/posts`，不要去改 `dist` 里的成品。** 下次构建时，成品会重新生成。

### 2. 每个名字分别负责什么

| 名字 | 通俗解释 |
| --- | --- |
| Markdown | 用少量符号写标题、列表、图片的文章格式，文件通常以 `.md` 结尾 |
| Astro | 把文章、页面和配置制作成网站的工具 |
| Fuwari | 当前主题，提供布局、配色、文章列表等结构 |
| Node.js | 让 Astro 等工具能在电脑上运行的环境 |
| pnpm | 安装项目依赖、运行项目命令的工具 |
| Corepack | 帮你按项目指定的版本调用包管理器；本文用它调用 pnpm |
| Git | 记录文件改动、保存历史版本的工具 |
| GitHub | 网上保存 Git 仓库和运行自动任务的平台 |
| GitHub Actions | GitHub 的自动任务功能，本项目用它构建和发布 |
| GitHub Pages | 提供静态网页访问的托管服务 |

**仓库**就是由 Git 管理的一套文件和历史记录。Git 是工具，GitHub 是平台，不要把两个名字混在一起。

当前项目声明使用 `pnpm@9.14.4`，本机核对到 Node.js `v22.19.0`。本文统一使用 `corepack pnpm`；如果电脑直接输入 `pnpm` 也能正常运行，它们调用的是同类项目命令。

### 3. 保存、提交、推送、部署是四件事

| 动作 | 改变了哪里 | 到这里是否已经上线 |
| --- | --- | --- |
| 保存，`Ctrl+S` | 电脑上的文件 | 没有 |
| 提交，`git commit` | 本机 Git 历史 | 没有 |
| 推送，`git push` | GitHub 仓库中的提交 | 还要看部署结果 |
| 部署成功 | 网站托管的网页文件 | 这次更新才会发布出去 |

例如，你把 `draft: true` 改成 `draft: false`：

1. 只保存，还只在电脑上。
2. 提交以后，只是本地历史有了这项改动。
3. 推送以后，GitHub 才拿到这个提交。
4. 部署任务构建并发布成功，线上才会换成包含文章的新版本。

所以，“push 后怎么还是旧的”要先查部署是否成功，不能只反复刷新。

### 4. 用 AI 帮忙时，也要看结果

可以让 AI 改错别字、解释报错、整理排版，但要说清楚允许修改哪些文件。

修改后至少做三件事：看 `git diff`、打开本地预览、运行构建。特别留意 AI 有没有顺手改了其他页面、删了文章、改了路径，或者把草稿改成公开。

不理解一段改动时，可以让它逐项解释。**“它说已经完成”不能代替实际预览和检查。**

## 三、项目里的文件去哪里找

**目录**就是文件夹。下面只列维护时常用的部分：

```text
blog-astro/

│  │  └─ spec/

│  ├─ data/friends.ts             友链名单
│  ├─ pages/                      各个页面和文章网址的生成规则
│  ├─ components/                 多个页面复用的小部件
│  ├─ layouts/                    页面的共同布局
│  ├─ styles/                     外观与排版规则

├─ scripts/new-post.js            新建文章脚本
├─ .github/workflows/
│  └─ deploy.yml                  GitHub Pages 部署任务

├─ .gitignore                    Git 通常不跟踪的文件规则
├─ node_modules/                 安装出来的依赖

└─ dist/                         构建出来的网页
```

最后三个目录可能要安装或运行项目后才出现。

“组件”可以理解成共用小部件，例如显示图片的组件；“模板”和“布局”负责页面的共同结构。**日常写文章，先只碰 Markdown 和自己的图片，不需要先修改模板。**

### 2. 哪些文件通常要进入 Git

通常要保存：文章、关于页正文、自己使用的图片、配置和页面源码、`package.json`、`pnpm-lock.yaml`、需要保留的部署配置。

通常不保存：`node_modules`、`dist`、`.astro`、运行日志、临时文件，以及含密码或令牌的文件。

项目的 `.gitignore` 已忽略这些生成目录以及 `.env`、`.env.production` 等文件。不是所有以点开头的文件都不能提交，`.gitignore` 和 `.github` 本身通常要保留。

**`pnpm-lock.yaml` 不是多余的缓存。** 它记录实际锁定的依赖版本，帮助自己的电脑和 GitHub 构建使用一致的依赖。不要为了“清理”随手删掉它。

不确定一个文件要不要添加，就先看用途和 `git status`。不要为了把列表清空而把所有文件一起提交。

## 四、终端入门：先确认自己在哪儿

### 1. 进入项目目录

推荐一直使用 VS Code 内置终端。打开“终端 → 新建终端”；若默认不是 PowerShell，在终端区域的下拉菜单中选择 PowerShell。

运行：

```powershell
Set-Location 'C:\code\blog-astro'
Get-Location
Test-Path .\package.json
```

它们依次表示：切换文件夹、显示当前文件夹、检查这里是否有 `package.json`。

正常结果应包含项目路径，最后一条显示 `True`。引号使用英文单引号。路径有空格时尤其需要保留引号。

想看看这里有什么文件，可以运行：

```powershell
Get-ChildItem
```

`Set-Location` 在 PowerShell 中也能简写成 `cd`。本文主要写全名，方便第一次见时理解。

### 2. 服务为什么一直占着终端

`corepack pnpm dev` 启动的是一个持续运行的预览服务。它要等待浏览器请求，并观察你有没有保存新内容，所以不会马上结束。

**这通常是正常运行，不是卡住了。** 保持它开着，去编辑器写文章即可。

要停止：点一下运行它的终端，按 `Ctrl+C`，等程序退出。

想保留预览，同时输入 Git 命令：点击终端区域的加号，另开一个 PowerShell。新窗口也先确认目录。不要在正在运行预览的窗口里继续粘贴下一批命令。

### 3. “找不到命令”和“找不到文件”分别查什么

**“无法识别 node / corepack / git”。** 先检查工具是否装好：

```powershell
node --version
corepack --version
git --version
```

成功时会显示版本号。这些命令不会改文章，也不会发布网站。

如果仍提示找不到，可能是没有安装，或终端没有读到新的工具路径。`PATH` 是系统查找命令时使用的目录清单；刚安装工具后，可以先关闭终端再重新打开。

本文不要求临时更换包管理器。如果 `corepack` 不存在，先把 Node.js 和 Corepack 环境准备好；不要把命令随手改成 `npm install`。

**“找不到 package.json”。** 先运行 `Get-Location`。通常是命令执行的文件夹不对，重新进入项目根目录即可。不要在桌面或文章文件夹里安装依赖。

### 4. 第一次克隆，与每天写文章不同

**克隆**是把网上仓库和它的历史记录下载到电脑。

如果 `C:\code\blog-astro` 已经是这个项目，不用再克隆。下面只适用于另一台电脑、目标目录还不存在的情况：

```powershell
Set-Location 'C:\code'
git clone https://github.com/Chalgen/blogFuwari.git blog-astro
Set-Location '.\blog-astro'
corepack pnpm install
```

`C:\code` 必须已经存在。不要让目标目录覆盖你想保留的现有文件。地址是当前个人仓库，不是 Fuwari 官方仓库。

第一次准备完成后，日常通常只需进入项目、启动预览、编辑文章。**不必每次克隆，也不必每次重新安装。**

### 5. Astro 遥测引起问题时怎么处理

遥测是工具收集使用情况的一项机制。如果当前环境因遥测而启动异常，可以在当前 PowerShell 设置：

```powershell
$env:ASTRO_TELEMETRY_DISABLED = '1'
corepack pnpm dev
```

第一条设置了一个**环境变量**，就是给接下来启动的程序传一项设置。它只影响当前终端及它启动的程序，关闭窗口后通常不会保留。

这不是日常必做步骤，也不能修复所有报错。项目的 GitHub Pages 工作流里已设置同一个变量。

## 五、本地预览：先在自己的电脑上看

### 1. 开发预览：边写边看

在项目根目录运行：

```powershell
corepack pnpm dev
```

成功后，终端会显示地址。当前项目带有 `/blogFuwari` 子路径，默认首页为：

```text
http://localhost:4321/blogFuwari/
```

`localhost` 表示自己的电脑，`127.0.0.1` 也是本机地址。把这种链接发给朋友，朋友不能靠它访问你电脑上的预览。

`4321` 是**端口号**，用来区分同一台电脑上的不同服务。如果它被占用，Astro 可能改用别的端口，终端会说明。以实际打印的地址为准。

保持服务运行，在编辑器修改文章并保存，再看浏览器。开发服务通常会更新页面。

### 2. 构建：检查能否做成正式网页

另开项目目录下的 PowerShell，运行：

```powershell
corepack pnpm build
```

本项目的 `build` 命令会依次：

1. 用 Astro 生成网页到 `dist`。
2. 用 Pagefind 为这些网页建立站内搜索索引。

**索引**可以理解成供搜索查阅的内容目录。搜索时不用临时逐个打开所有文章文件。

成功时，命令执行完毕，会回到可输入状态。如果失败，往上找第一个具体错误，不要只看末尾“退出码为 1”。

构建只更新本机成品，**不代表上传或上线**。

### 3. 构建预览：检查准备发布的成品

构建成功后运行：

```powershell
corepack pnpm preview
```

打开终端给出的地址，保留 `/blogFuwari/` 路径。它读取的是 `dist`，适合发布前检查。

| 对比项 | 开发预览 `dev` | 构建预览 `preview` |
| --- | --- | --- |
| 用途 | 写作时随改随看 | 检查构建好的成品 |
| 本项目是否显示草稿 | 显示 | 不显示 |
| 保存源码后的变化 | 开发服务通常更新 | 需要重新 build |
| 搜索数据 | 可能没有索引，或沿用旧索引 | 使用本次构建生成的索引 |

想同时保留两种预览，可给构建预览指定另一个端口：

```powershell
corepack pnpm preview --port 4323
```

若端口可用，首页为 `http://localhost:4323/blogFuwari/`。看完按 `Ctrl+C` 停止。

## 六、新文章怎么写：先弄懂开头的资料栏

### 1. 两条 `---` 中间是什么

**Frontmatter** 就是文章最上面的资料栏。它不是正文，而是告诉博客：标题、日期、分类、是否公开等信息。

项目按 `src/content/config.ts` 中的 **schema** 检查这些内容。Schema 可以理解为“允许填哪些栏目、每栏填什么”的规则表。

最小的草稿模板：

```markdown
---
title: '我的第一篇记录'
published: 2026-10-26
draft: true
---

这里开始写正文。
```

规则中，`title` 和 `published` 必填；`draft` 可以不写，但**不写默认公开**。初学者建议每次明确写出来。

### 2. 常用完整模板

**文件内容：复制到新建的 `.md` 文件。**

```markdown
---
title: '我的第一篇记录'
published: 2026-10-26
draft: true
description: '记录今天学到的一件小事。'
image: ''
tags: ['生活记录', '学习']
category: '随笔'
lang: 'zh_CN'
---

先用一小段话说明这篇文章想分享什么。

## 事情的经过

在这里写正文。

## 我的想法

在这里写自己的感受。
```

替换示例标题、日期、简介、标签、分类和正文。没有封面就保留 `image: ''`，不需要标签就写 `tags: []`。

以后对文章做了实质修改，可以补充一行更新日期，例如：

```yaml
updated: 2026-10-26
```

### 3. 每个字段具体填什么

| 字段 | 意思 | 要求与默认值 |
| --- | --- | --- |
| `title` | 显示的文章标题 | 必填，文字 |
| `published` | 发布日期，也用于排序 | 必填，日期 |
| `updated` | 内容更新日期 | 可选，不填就没有这个值 |
| `draft` | 是否作为草稿 | 可选，默认 `false` |
| `description` | 文章简介 | 可选，默认 `''` |
| `image` | 封面地址 | 可选，默认 `''`，不显示封面 |
| `tags` | 多个关键词 | 可选，文字数组，默认 `[]` |
| `category` | 一个分类 | 可选，文字或 `null`，默认 `''` |
| `lang` | 文章语言 | 可选，默认 `''`，页面使用站点语言 |

“文字”在配置中也叫**字符串**。“数组”是一组值，用方括号包起来。

分类像书架，一篇文章在当前规则中只放进一个分类；标签像便签，可以贴多个：

```yaml
category: '使用手册'
tags: ['Git', 'Markdown', '博客维护']
```

不要把 `category` 写成数组，也不要把 `tags` 写成一段逗号分隔的普通文字。

`prevTitle`、`prevSlug`、`nextTitle`、`nextSlug` 是程序安排上一篇和下一篇时使用的内部字段，不用手填。

### 4. YAML 最容易写错的地方

资料栏使用 **YAML**，一种用“名称：值”保存配置的格式。先记住：

1. 冒号是英文 `:`，后面留一个空格。
2. 引号用英文 `'` 或 `"`，不要用中文弯引号 `“”` 替代。
3. 日期按示例写成 `2026-10-26`，这里不加引号，方便按日期解析。
4. 开关 `true`、`false` 不加引号；`draft: 'false'` 是文字，不是正确开关。
5. 这类简单资料栏每行从最左边开始，不要随意缩进，不要用 Tab 对齐。
6. 标题含冒号、井号等符号时，用英文引号包住整段文字。

例如：

```yaml
title: '今天的记录：第一次写博客'
description: '先写清楚内容，再慢慢调整排版。'
image: ''
tags: []
```

`''` 是空文字，`[]` 是空数组，`null` 是没有值。它们不是同一种东西。

不要把可选字段都留成 `字段名:`。例如 `image:` 会读成空值，但当前规则要求文字；没有封面就写 `image: ''`。

若标题带英文单引号，可以换用英文双引号包住，例如 `title: "Today's note"`。拿不准时先用简单标题，确认能构建，再慢慢加内容。

### 5. 文件名、文件夹与文章网址

标题决定页面显示的名字；**文件路径通常决定文章网址**。它们可以不同。

| 文件位置 | 当前站点内的文章路径 |
| --- | --- |
| `posts/my-first-note.md` | `/blogFuwari/posts/my-first-note/` |
| `posts/my-first-note/index.md` | `/blogFuwari/posts/my-first-note/` |
| `posts/travel/day-one.md` | `/blogFuwari/posts/travel/day-one/` |

表格中的 `posts` 指 `src/content/posts`。前两行是两种组织方式，**不要同时创建同名普通文章和目录式文章**，以免网址冲突。

目录式文章就是为文章建立单独的文件夹，把正文命名为 `index.md`，相关图片放在旁边：

```text
posts/
└─ my-first-note/
   ├─ index.md
   └─ photo.jpg
```

只改 `title`，一般不改网址。改文件名、目录名或把文件移到别处，则可能使网址变化，旧链接可能失效。公开后尽量少改路径。

文件名建议简短、小写英文加连字符，如 `my-first-note.md`。不是不能用中文，而是这样更方便复制链接、检查大小写和编码。

### 6. 草稿与日期：为什么本地有、线上没有

当前项目在 `src/utils/content-utils.ts` 中区分环境：

- 开发预览包含草稿，方便写作检查。
- 正式构建排除 `draft: true` 的文章。
- 构建预览和 GitHub Pages 使用正式成品，因此也没有草稿。
- 正常构建生成的分类、标签、RSS 和搜索索引，也不包含这些草稿。

准备公开时改为：

```yaml
draft: false
```

然后保存、构建、提交、推送，并检查部署成功。不需要删除重建文件。

**`published` 是显示日期和排序依据，不是定时发布开关。** 填未来日期，也不能指望它自动等到那天才公开。暂时不公开，用 `draft: true`。

修改错别字或补充正文，通常保留原来的 `published`；较大改写可以增加或更新 `updated`。本篇也保留首次日期，另记重写日期。

草稿不是保密存储。推到公开仓库以后，别人仍可能从源码阅读草稿。不要放密码、Cookie 或私人令牌。

### 7. 用脚本新建文章，要留意默认值

熟悉手工新建以后，可以在项目根目录运行：

```powershell
corepack pnpm new-post my-second-note
```

它会创建 `src/content/posts/my-second-note.md`，日期取运行时本机日期；同名文件已存在时会报错，不会覆盖。

**当前脚本生成 `draft: false`。** 想先写草稿，请创建后立即改成 `draft: true`。脚本只帮你创建文件，不会替你上线。



## 七、用 Git 保存版本：跟着一篇文章走一遍

### 1. 先认识五个词

Git 不是普通的“自动保存”。它让你决定：这次把哪些改动组成一个版本，并为这个版本写一句说明。

| 词语 | 可以怎样理解 |
| --- | --- |
| 工作区 | 你现在正在编辑的文件 |
| 暂存区 | 放入“这次准备保存”的改动清单 |
| 提交 | 把清单正式记录为一个本地版本 |
| 分支 | 一条独立发展的版本路线，当前主要使用 `main` |
| 远程仓库 | 网上与本地交换提交的另一份仓库 |

日常过程是：**编辑文件 → 检查改动 → 选入暂存区 → 提交 → 推送。**

暂存并不会删掉文件，也不会让网页上线。提交保存的是当时已暂存的改动；暂存以后又编辑文件，需要再次添加，新增修改才会进入这次提交。

### 2. 先看看自己改了什么

在项目根目录的 PowerShell 运行：

```powershell
git status
```

它会告诉你当前分支，以及哪些文件已修改、已暂存或尚未跟踪。

**未跟踪文件**就是 Git 目前还没有纳入版本记录的新文件。例如刚创建的 `my-first-note.md`。

继续检查已经跟踪的文件：

```powershell
git diff
```

它主要展示“工作区相对于暂存区”的差异。差异里，`+` 开头通常代表新增内容，`-` 开头通常代表删除内容，这些符号是展示方式，不是要加到文件里的正文。

**新建的未跟踪文件不一定出现在普通 `git diff` 中。** 所以不能只看它没有输出，就认为没有改动。新文章先在编辑器打开，完整读一遍，再结合 `git status` 检查。

### 3. 只添加这次要保存的文件

确认本次就是保存前面创建的练习文章后，运行：

```powershell
git add -- 'src/content/posts/my-first-note.md'
```

`--` 是用来明确后面是文件路径的分隔符，路径需要与实际文件一致。

如果是修改本篇手册，路径就换成：

```powershell
git add -- 'src/content/posts/blog-handbook.md'
```

**这两条是不同场景的示例，不要求一起执行。** 新文章有配图时，还要分别添加实际新增的图片。

初学时先不用 `git add .`，因为它可能把当前目录下其他未检查的修改也一起加进去。例如不相关的配置改动或误删文件。

### 4. 看看这次提交到底会包含什么

添加之后，运行：

```powershell
git diff --cached
git status
```

`--cached` 表示检查暂存区。这里应该能看到刚添加的新文章，以及你确实想保存的其他内容。

如果出现不相关文件，先取消那个文件的暂存：

```powershell
git restore --staged -- '实际的文件路径'
```

“实际的文件路径”是占位文字，要替换。这个命令只把文件从本次提交清单中移出，**保留工作区内容**，不会删掉你刚写的文章。

### 5. 提交一个本地版本

检查完成后再运行：

```powershell
git commit -m '新增：我的第一篇记录'
```

引号内是这次改动的说明，可以换成更符合实际的一句话，例如“修正文章中的图片路径”。不要每次都写“修改”而完全看不出改了什么。

成功以后，Git 会显示一个提交编号。查看最近的版本：

```powershell
git log -5 --oneline
```

`-5` 表示最多看五条，`--oneline` 表示每条简短显示。想看某次具体改动，可使用 `git show 提交编号`，把占位文字换成实际编号。

某些 Git 查看界面会进入可滚动的阅读窗口；按 `q` 可以退出，回到终端。

### 6. 推到哪里：先确认分支和远程

运行：

```powershell
git remote -v
git branch --show-current
git branch -vv
```

依次查看远程地址、当前分支、分支的跟踪关系。**跟踪关系**是本地分支与某个远程分支之间的对应设置。

这份手册整理时，本项目是：

| 名称 | 实际对象 |
| --- | --- |
| 当前分支 | `main` |
| `origin` | `https://github.com/Chalgen/blogFuwari.git`，当前个人博客仓库 |
| `upstream` | `https://github.com/saicaca/fuwari.git`，官方主题仓库 |
| 本地 `main` 的跟踪分支 | `origin/main` |

`origin`、`upstream` 只是名字，本身不保证谁是个人仓库、谁有写入权限。**看实际地址，不只背名称。**

只有当地址和分支仍然符合上表，并且准备发布当前提交时，才使用：

```powershell
git push origin main
```

这会把本地 `main` 上传到 `origin` 的 `main`。不要把个人文章推到官方 Fuwari 的 `upstream`。

如果在另一份项目里还没有自己的远程仓库，需要先在 GitHub 准备自己的仓库、设置正确地址与登录权限。不要套用未知的 push 目标。如果推送被拒绝，先看错误，不要用强制推送绕过去。

## 八、Markdown 入门：先写清楚，再学排版

Markdown 的特点是：正文仍然可以像普通文字一样写，需要标题、列表等结构时，再加少量符号。

以下标成“源码”的内容写入 `.md` 正文，不放进 PowerShell。你在编辑器看见符号，在网页上看见排版，这是正常的。

### 1. 标题：用井号表示层级

**源码：**

```markdown
## 今天的记录

### 上午做了什么

#### 一个小补充
```

**效果：** 分别成为二级、三级、四级标题。井号后面留一个空格。

文章顶部已经由模板展示了 `title`，所以正文通常从 `##` 开始，再按需要用 `###`。不要为了字大而把所有句子都设为标题。

项目已经开启自动目录，系统按正文标题生成。目录是否在当前屏幕上显示还与页面布局、宽度有关；不用再手写一份容易过期的目录。

### 2. 段落：中间空一行

**源码：**

```markdown
这是第一段，可以写几句话。

这是第二段，开始讲另一件事。
```

**效果：** 两个独立段落，中间有段落间距。

在编辑器里，一行太长自动折到下一行，是编辑器为了方便阅读的显示，不代表你插入了新的段落。

### 3. 普通单换行，为什么不一定分成两行

**源码：**

```markdown
窗边有一盏灯。
我把今天写下来。
```

**效果：** 在当前 Markdown 渲染方式下，它们仍在同一个段落中，不会因为这一个回车就生成 `<br>` 换行。浏览器按可用宽度排版，也可能在中间显示一点空隙。

实际示范：

窗边有一盏灯。
我把今天写下来。

如果你写小说，每次回车其实是新一段对话，通常应该在两段之间留空行。

如果你写诗，希望“这里必须换行”，可以使用 `<br>`：

```markdown
窗边有一盏灯。<br>
我把今天写下来。
```

实际示范：

窗边有一盏灯。<br>
我把今天写下来。

Markdown 也支持在上一行末尾留两个空格再回车，但空格看不见，编辑器还可能清掉行尾空格，所以初学时 `<br>` 更容易检查。

一整段诗都想保留源码换行，可以看后面的局部排版示例。不要靠连续空行制造一大块留白。

### 4. 加粗、斜体、删除线

**源码：**

```markdown
这是 **需要注意的内容**。
这是 *轻一点的强调*。
这是 ~~不再适用的说法~~。
```

**效果：**

这是 **需要注意的内容**。这是 *轻一点的强调*。这是 ~~不再适用的说法~~。

成对符号里面不要多留首尾空格，例如尽量写 `**重要**`，而不是 `** 重要 **`。

中文字体未必有好看的专门斜体，重要信息一般用加粗或提示块更清楚。

### 5. 分隔线

**源码：**

```markdown
这一部分结束。

---

下面进入另一部分。
```

**效果：** 正文中间出现一条分隔线。

上下留空行，避免它与标题写法或其他结构混淆。文章最顶部的两条 `---` 用来包住资料栏，与正文分隔线所处的位置不同。

### 6. 无序列表、有序列表、嵌套列表

**源码：**

```markdown
- 先写内容
- 再检查图片
- 最后预览

1. 打开项目
2. 启动预览
3. 保存文章

- 发布前检查
    - 图片是否加载
    - 手机上是否好读
```

**效果：** 第一组带圆点，第二组带步骤编号，最后一组有缩进的子项目。

列表符号后留空格。子列表比父项缩进，本文示例使用四个空格。不要用中文全角空格来假装缩进。

### 7. 任务列表

当前项目支持这种清单：

```markdown
- [x] 写完正文
- [ ] 检查图片
- [ ] 确认部署成功
```

**效果：**

- [x] 写完正文
- [ ] 检查图片
- [ ] 确认部署成功

`[x]` 表示完成，`[ ]` 表示未完成。网页里通常是展示用的勾选框，不是给访客保存进度的待办软件；要修改状态，仍需改 Markdown 文件。

### 8. 链接、站内链接与章节链接

**源码：**

```markdown
[打开当前博客](https://chalgen.github.io/blogFuwari/)

[阅读关于页](/blogFuwari/about/)
```

**效果：** 方括号里的文字变成可以点击的链接，圆括号里是访问地址。

“站内链接”就是链接到同一网站的页面。当前网站放在 `/blogFuwari/` 子路径中，普通 Markdown 里的 `/about/` 会指向域名根目录，不会自动变成 `/blogFuwari/about/`。

因此，上面的站内示例明确写入当前前缀。如果以后换子路径或改成独立域名的根目录，这类文章链接也要检查。

**锚点链接**是跳到某一节的地址，通常带 `#`。本项目会为标题生成锚点。最稳妥的办法是在预览中找到标题旁的 `#`，点击后复制浏览器地址，而不是猜中文标题会生成什么编号。标题改名后，旧锚点也可能变化。

不用为了这一功能手写整篇目录。

### 9. 图片和替代文字

**源码，当前仓库中已有这张主题示意图：**

```markdown
![主题自带的示意头像，用来说明图片写法](../../assets/images/demo-avatar.png)
```

**效果：** 页面展示图片，而不是显示这串符号。下面就是实际示范：

![主题自带的示意头像，用来说明图片写法](../../assets/images/demo-avatar.png)

方括号中的文字叫**替代文字**。图片加载失败或使用读屏软件时，它能帮助理解图片内容。不要所有图片都只写“图片”。

路径与普通文字不同，必须真正对应一个文件。更详细的封面、正文图片和 `public` 路径区别，在“图片怎么放”一章。

### 10. 引用

**源码：**

```markdown
> 这里是一段引用或补充说明。
>
> 想在引用里分段，中间保留带有大于号的空行。
```

**效果：**

> 这里是一段引用或补充说明。
>
> 想在引用里分段，中间保留带有大于号的空行。

引用别人的文字时，记得说明出处。`>` 是英文大于号。

### 11. 表格

**源码：**

```markdown
| 项目 | 说明 |
| --- | --- |
| 保存 | 更新本机文件 |
| 推送 | 上传本地提交 |
```

**效果：**

| 项目 | 说明 |
| --- | --- |
| 保存 | 更新本机文件 |
| 推送 | 上传本地提交 |

第二行的分隔不能省。竖线 `|` 用来分开列。

Markdown 表格适合少量对照信息，不适合复杂合并单元格，也不适合把一篇长文章塞进格子。手机屏幕窄，尽量控制列数、缩短每格内容；长代码放到表格外。

单元格里需要显示竖线，可以尝试转义 `\|`，或换一种更简单的表达。

### 12. 行内代码、代码块和语言标记

讲到命令名、字段名时，可以用一对英文反引号：

```markdown
把 `draft` 改成 `false`。
```

**效果：** 把 `draft` 改成 `false`。这是**行内代码**，不需要真的执行。

多行命令或文件示例则使用**代码块**：开头、结尾各一行三个反引号。为了在本篇里展示这三个反引号，外层示例使用四个反引号：

````markdown
```powershell
Get-Location
git status
```
````

**效果：** 两条命令放进独立代码框，不会被当正文排版。

开头的 `powershell` 是语言标记，帮助代码着色；它不会让网页自动执行命令。常见标记有 `markdown`、`yaml`、`html`、`css`、`javascript`、`powershell`。普通输出或目录树可写 `text`。

结尾的反引号数量要与开头匹配，且单独成行。忘记结束围栏，后面的正文可能全部被当成代码。

### 13. 特殊符号如何原样显示

有些符号会被 Markdown 识别。想让它保持普通文字，可以在前面加英文反斜杠：

```markdown
\*这不是斜体\*
\# 这不是标题
```

**效果：** 显示星号和井号本身，而不形成斜体或标题。

命令、文件路径等一整段内容，通常直接放进反引号更方便。不要把 Windows 文件路径的反斜杠与网页路径的正斜杠混用。

### 14. 正文里出现 HTML 怎么办

**HTML** 是描述网页结构的标记。当前 `.md` 渲染流程允许原始 HTML，例如：

```html
<p>这是一段 HTML 文字。<br>这里明确换行。</p>
```

**效果：** 生成段落和换行。HTML 元素通常由开始标签和结束标签组成，例如 `<p>` 与 `</p>`。

在 HTML 块里，初学时直接使用 HTML，不要假定里面的 Markdown 一定会继续解析。例如需要加粗就写 `<strong>重要</strong>`。

如果你只是想展示 HTML 源码，必须放入代码块，否则它可能被当成真正的网页标签。不要随便复制来路不明的 `<script>` 或整段网页代码。

## 九、文字怎么变大、换字体、改颜色

### 1. 先分清自己到底想改什么

这几件事看起来相近，其实由不同规则控制：

| 想改变什么 | 对应的概念或写法 |
| --- | --- |
| 表达“这句话很重要” | 文字强调，例如 Markdown 加粗 |
| 字变大或变小 | 字号，`font-size` |
| 换一种字的样子 | 字体家族，`font-family` |
| 字变细或变粗 | 字重，`font-weight` |
| 两行之间更松一些 | 行高，`line-height` |
| 字换颜色 | 文字颜色，`color` |

**CSS** 是描述网页外观的规则。`font-size` 这类英文名，就是一项具体规则的名称。

普通 Markdown 没有通用的“设置字体、字号、颜色”语法。某个笔记软件里的专属写法，不能直接认为博客也支持。

### 2. 只改一小段：可直接使用的例子

如果只想突出一小段话，可以把下面的**文件内容**写入 Markdown 正文：

```html
<p style="font-size: 1.125rem; line-height: 1.9; font-weight: 600; color: var(--primary);">
请先预览，确认没有问题，再公开文章。
</p>
```

实际效果：

<p style="font-size: 1.125rem; line-height: 1.9; font-weight: 600; color: var(--primary);">
请先预览，确认没有问题，再公开文章。
</p>

这里可以逐项看：

- `style`：只给这一个元素填写外观规则，称为**行内样式**。
- `font-size: 1.125rem`：相对于网页根字号稍微放大；不是 Word 的“几号字”。
- `line-height: 1.9`：行高为当前字号的 1.9 倍。
- `font-weight: 600`：偏粗；不保证每种字体都有独立的 600 字形。
- `color: var(--primary)`：使用博客当前主题色，而不是写死一个颜色。
- 每条规则用英文冒号分开名称和值，用英文分号结束。

`rem` 会参考网页根字号，`px` 则是网页的 CSS 像素单位，都不能直接与印刷字号等同。初学时可以保留例子中的数值，不必急着设计整套字号。

### 3. 想让诗句保留每次回车

把下面内容放进文章正文即可：

```html
<p style="white-space: pre-line; line-height: 2; font-family: serif;">窗边有一盏灯。
我把今天写下来。
明天再翻开这一页。</p>
```

实际效果：

<p style="white-space: pre-line; line-height: 2; font-family: serif;">窗边有一盏灯。
我把今天写下来。
明天再翻开这一页。</p>

`white-space: pre-line` 会保留源码换行，同时合并多余空格；它与普通 Markdown 单换行不同。`serif` 表示请求系统的衬线字体，实际中文样子取决于读者设备。

这个方法适合一小段诗。小说正文如果想分成段落，仍优先用空行分段。

### 4. 局部样式与全站样式的区别

**局部样式**只影响指定片段；**全站样式**会影响许多页面。想改一小段，不要先去改全站字体。

如果很多文章反复使用同一种样式，以后可以给它一个有含义的**类名**。类名就像标签，正文贴标签，样式文件负责解释标签应该长什么样。

例如，未来可以在 `src/styles/markdown.css` 增加：

```css
.custom-md .reading-note {
    font-size: 1.125rem;
    line-height: 1.9;
    color: var(--tw-prose-body);
}
```

再在文章中写：

```html
<p class="reading-note">这段文字使用统一的阅读提示样式。</p>
```

**这是以后维护样式的方法示例，当前没有新增这条类规则。** 只复制第二段、不添加第一段规则，不会自动获得这种新样式。前面两个行内样式例子则可以直接用。

`.custom-md` 把影响范围限制在 Markdown 正文里，减少误改导航和其他页面的机会。

### 5. 真要改全站字体，去哪里改

当前主要位置是：

| 文件 | 负责的事情 |
| --- | --- |
| `tailwind.config.cjs` | `theme.extend.fontFamily.sans` 中的默认字体列表 |
| `src/layouts/Layout.astro` | 导入 Roboto 的 400、500、700 字重资源 |
| `src/styles/markdown.css` | 正文细节和行内代码样式 |
| `src/styles/markdown-extend.styl` | 提示块等扩展样式 |
| `astro.config.mjs` | 包含代码块的字体、字号和行高配置 |
| `src/components/misc/Markdown.astro` | 导入 JetBrains Mono 代码字体 |

也就是说，正文默认字体、行内代码字体、代码框字体不是一个开关。

如果以后要调整正文的中文后备字体，可以在 `tailwind.config.cjs` 中替换原有的 `sans` 属性值，例如：

```javascript
sans: ['Roboto', 'Microsoft YaHei', 'PingFang SC', 'Noto Sans CJK SC', ...defaultTheme.fontFamily.sans],
```

这是**替换一个属性的示例**，不能当成完整配置覆盖整个文件。本篇只解释位置，不要求你现在修改全站字体。

修改这类配置后，可能需要停止并重启开发服务，再检查正文、加粗、代码和手机页面。

### 6. 后备字体列表是什么

`font-family` 后面可以写多个字体名称。浏览器会尝试用前面的字体显示某个字，没有合适字形时，再找后面的字体。

例如 Roboto 主要覆盖拉丁文字，中文通常由后面的字体提供。**写了一个字体名称，不等于网站会自动下载它。** 没有安装也没有提供字体文件时，浏览器会继续找后面的字体。

当前默认配置中，通用的 `sans-serif` 放得较早。如果以后要指定中文字体的优先级，应把具体字体放在通用后备之前。

### 7. 系统字体、在线字体、本地托管字体

- **系统字体**：读者设备上已经有的字体，通常不用下载，但不同设备的字形可能不同。
- **在线字体**：从别的服务器获取字体，可能受网络、服务可用性和加载速度影响。
- **本地托管字体**：项目提供字体资源，由自己的网站加载；也会产生下载体积，并不是“完全不用下载”。

当前通过 Fontsource 引入的字体属于随项目构建提供的资源，不要求访客临时去 Google Fonts 下载。

中文字体字数多，完整文件可能很大。以后引入字体时，要考虑加载速度、实际需要的字重、适合网页的格式和字体授权。拿到字体文件不等于有权公开分发；不要为了统一字形一口气加载多套完整中文字库。

中文也不一定有专门设计的斜体，浏览器可能只是把字机械倾斜。加粗、斜体、字体大小和字体家族，是不同问题。

### 8. 颜色与排版的几个底线

固定黑字可能在深色模式看不清，固定白字可能在浅色模式消失。优先沿用主题变量，例如正文色 `var(--tw-prose-body)` 或主题色 `var(--primary)`，仍要检查两种模式是否清楚。

不要只靠颜色表达“危险”或“完成”，还要写出文字。

不要把普通段落放大后假装标题，否则自动目录不知道它是标题。不要用全角空格、连续空行或很多 `<br>` 对齐布局，手机屏幕一变窄就容易乱。

### 9. Markdown 和 MDX 有什么不同

**MDX** 是能在 Markdown 中进一步使用组件和程序表达式的格式。它需要相应支持，不是简单改个后缀就行。

当前没有配置 `@astrojs/mdx` 集成。虽然新建脚本接受 `.mdx` 后缀，也不能据此认为整套 MDX 已接入。普通文章继续用 `.md` 即可，偶尔调一段字号不需要改用 MDX。

## 十、当前 Fuwari 还能写哪些内容

下面按本项目配置介绍，不照搬其他主题的专属写法。

### 1. 提示块：把注意事项单独放出来

**源码：**

```markdown
:::tip[写作提醒]
先保存，再去浏览器查看。
:::
```

实际效果：

:::tip[写作提醒]
先保存，再去浏览器查看。
:::

开头和结尾的三连冒号都要保留。当前配置支持 `note`、`tip`、`important`、`caution`、`warning` 五类，方括号里是自定义标题。

也支持 GitHub 风格提示，例如：

```markdown
> [!NOTE]
> 这也是一段提醒。
```

不要直接套用 Hexo、Butterfly 等主题的 `{% ... %}` 专属语法，当前项目没有因此自动获得那些功能。

### 2. 折叠说明

**源码：**

```html
<details>
<summary>点这里展开补充说明</summary>
<p>这里放不想一开始占太多空间的内容。</p>
</details>
```

实际效果：

<details>
<summary>点这里展开补充说明</summary>
<p>这里放不想一开始占太多空间的内容。</p>
</details>

点击标题展开，再点收起。里面使用 HTML 段落，避免混用后不确定 Markdown 是否会解析。

折叠只是阅读效果，不是密码保护，展开内容仍然在网页里。

### 3. 一小段防剧透

**源码：**

```markdown
这道题的答案是 :spoiler[先检查，再发布]。
```

实际效果：

这道题的答案是 :spoiler[先检查，再发布]。

这是主题样式提供的遮挡效果，不能用来保护秘密。

### 4. 代码高亮、行号和重点行

当前使用 **Expressive Code**，负责代码的着色、行号、折叠等展示。

**源码，外层四反引号仅用于展示：**

````markdown
```javascript title="示例.js" showLineNumbers {2}
const message = '文章已经保存';
console.log(message);
```
````

实际效果：

```javascript title="示例.js" showLineNumbers {2}
const message = '文章已经保存';
console.log(message);
```

- `title` 是代码框标题，不是实际创建文件。
- `showLineNumbers` 显示行号。
- `{2}` 突出第二行。
- `showLineNumbers=false` 可对单个代码块关闭行号。

当前配置默认让代码折行，`shellsession` 类型单独关闭行号。语言标记影响展示，不会执行代码。

长代码还能指定折叠范围：

````markdown
```javascript collapse={1-2}
// 这两行说明可以折叠
// 点击代码块里的折叠区域查看
console.log('保留显示的代码');
```
````

实际效果：

```javascript collapse={1-2}
// 这两行说明可以折叠
// 点击代码块里的折叠区域查看
console.log('保留显示的代码');
```

代码框有自定义复制按钮，当前样式在鼠标移上去时更明显。浏览器剪贴板权限、HTTPS 和设备操作方式会影响复制体验；不成功时可以手动选择代码复制。行号是展示，不要把它手抄进命令。

### 5. 数学公式

当前配置了 `remark-math` 和 KaTeX，可以写：

```markdown
行内公式：$a^2 + b^2 = c^2$。

$$
E = mc^2
$$
```

实际效果：行内公式 $a^2 + b^2 = c^2$。

$$
E = mc^2
$$

单美元用于行内，双美元包住独立公式。这里不是完整的 LaTeX 文档编译器，复杂命令需确认 KaTeX 是否支持。

当前 `pagefind.yml` 排除了公式节点，不要用公式本身是否能搜到判断站内搜索正常与否。

### 6. 视频和音频

当前允许 HTML，所以可以使用浏览器原生的视频、音频标签。**下面仅为需要准备文件后才能使用的源码示例，本篇没有加载这些不存在的媒体：**

```html
<video controls preload="metadata" style="width: 100%; height: auto;">
  <source src="/blogFuwari/media/my-video.mp4" type="video/mp4">
  你的浏览器无法播放这个视频。
</video>

<audio controls preload="none" style="width: 100%;">
  <source src="/blogFuwari/media/my-audio.mp3" type="audio/mpeg">
  你的浏览器无法播放这个音频。
</audio>
```

要用它，先把有权发布的真实文件放到 `public/media/`，再替换文件名，并保留当前站点的 `/blogFuwari` 前缀。视频很大时不适合随意放进 Git 仓库，应先考虑合适的托管方式。

平台提供的 iframe 嵌入代码也可能使用，但平台必须允许嵌入。普通分享页面地址不一定能当播放器地址；外部访问、登录和版权限制也可能导致失败。

### 7. GitHub 卡片与尚未接入的能力

本项目配置了仓库卡片指令：

```markdown
::github{repo="saicaca/fuwari"}
```

它依赖 GitHub 接口，网络不通或限流时可能加载失败，不需要在文章中填个人令牌。

当前没有接入专用音乐播放器、音乐解析接口、MDX 集成或 Mermaid 图表渲染。**一段示例代码、一个分享链接，不等于网站已经有完整功能。** 普通文章不用为此添加依赖。



## 十一、图片怎么放：正文、封面、头像和横幅别混在一起

### 1. 四种图片，入口不同

| 图片用途 | 在哪里设置 |
| --- | --- |
| 正文插图 | Markdown 正文里的 `![说明](路径)` |
| 文章封面 | 文章资料栏的 `image` |
| 个人头像 | `src/config.ts` 的 `profileConfig.avatar` |
| 站点横幅 | `src/config.ts` 的 `siteConfig.banner` |

正文里插入一张图，不会自动变成封面。换头像，也不会自动打开横幅。

当前头像配置为 `/images/a.jpeg`，文件在 `public/images/a.jpeg`。当前横幅的 `enable` 为 `false`，所以即使配置了图片路径，也不会显示横幅。

### 2. `src` 和 `public` 有什么区别

**放在 `src` 中的图片**可以进入 Astro 的处理流程。例如 Markdown 引用项目内图片时，构建工具可以处理并生成新的资源文件名。不要依赖生成后的文件名，也不要手动维护 `dist/_astro` 里的图片。

本篇已有的示意图写法是：

```markdown
![主题自带的示意头像](../../assets/images/demo-avatar.png)
```

这里的起点是本篇 Markdown 所在的 `src/content/posts`。`..` 表示上一层，两个 `..` 先回到 `src`，再进入 `assets/images`。

如果新建目录式文章，并把图片放在 `index.md` 旁边，正文可以写：

```markdown
![请替换成这张照片的实际说明](./photo.jpg)
```

**使用这个例子前，必须真的准备好同目录的 `photo.jpg`。** `./` 表示当前目录。把文章搬到别处时，相对路径也要重新检查。

**放在 `public` 中的图片**通常按原文件复制到成品中，不走同样的图片优化流程。例如：

```text
public/images/a.jpeg
```

当前网站的浏览器访问路径是：

```text
/blogFuwari/images/a.jpeg
```

网址里没有 `public`，因为 `public` 是源码目录名，不是网页地址的一部分。

### 3. 为什么有时写 `/images`，有时要写 `/blogFuwari/images`

这是当前项目最容易混淆的地方：**组件里的配置，会不会帮你补子路径，要看具体实现。**

当前 `src/components/misc/ImageWrapper.astro` 会为以 `/` 开头的 public 图片调用项目的 `url()` 工具，补上 `base`。

所以头像和文章封面这类交给 ImageWrapper 的配置，可以写：

```yaml
image: '/images/a.jpeg'
```

它会生成类似 `/blogFuwari/images/a.jpeg` 的图片地址。这里复用了已有文件，只是说明路径，不代表建议把头像当文章封面。

但**普通 Markdown 或手写 HTML 里的根路径，不会因为用了同样的文字就自动经过 ImageWrapper**。在当前子路径站点中，应写：

```markdown
![项目已有的头像文件，仅用于演示路径](/blogFuwari/images/a.jpeg)
```

或用 HTML 控制局部显示尺寸：

```html
<img src="/blogFuwari/images/a.jpeg" alt="项目已有的头像文件，仅用于演示路径" width="120" style="max-width: 100%; height: auto;">
```

下面是这个 HTML 的实际示范：

<img src="/blogFuwari/images/a.jpeg" alt="项目已有的头像文件，仅用于演示路径" width="120" style="max-width: 100%; height: auto;">

**不要在已经自动补 `base` 的头像或封面配置里再手工加一遍 `/blogFuwari`**，否则可能重复前缀。普通 Markdown 中写死前缀的地址，以后换站点路径时则需要一起检查。

对于经常随文章一起移动的正文图片，优先考虑同目录相对路径，能少记一些站点前缀。

### 4. 当前 ImageWrapper 可用的封面写法

**没有封面：**

```yaml
image: ''
```

这是正常情况，不需要虚构封面地址，也不必为了让资料栏“填满”随便找图。本篇就没有封面。

**引用 public 中实际存在的图片：**

```yaml
image: '/images/a.jpeg'
```

**本篇这种直接放在 `posts` 下的文章，引用 src 中已有图片：**

```yaml
image: '../../assets/images/demo-banner.png'
```

**目录式文章引用与 `index.md` 同目录的封面：**

```yaml
image: './cover.jpg'
```

最后一个例子要求该目录中真实存在 `cover.jpg`。当前组件会按文章文件所在目录计算相对图片路径；文章移动以后不能只看字符串不变，还要确认相对位置没变。

以 `https://` 开头的外链图片也会按外部地址处理，但对方删除图片、防盗链或网络异常都会使它失效。

### 5. 电脑磁盘路径不能当网页图片地址

下面是电脑文件位置，不是公开网页地址：

```text
C:\Users\你的用户名\Pictures\photo.jpg
```

访客没有你的硬盘，网站也不能这样读取你电脑上的文件。先把有权发布的图片放进项目，再按项目相对路径或 public 访问路径引用。

网页路径用正斜杠 `/`。Windows 文件位置常用反斜杠 `\`，二者不能随意混用。

### 6. 文件名、尺寸、格式和授权

Windows 常常不严格区分大小写，部署用的 Linux 环境却可能区分。例如 `photo.jpg`、`Photo.jpg`、`photo.JPG` 不能想当然看成一样。仓库里也确实存在大写扩展名的图片，引用时应完全匹配。

空格和中文文件名在网址中可能变成百分号编码，不一定是坏了，但更不方便排查。新配图可以用简短英文文件名，例如 `desk-note.webp`；不要为了统一风格随便重命名已经被引用的旧文件。

上传前可以检查：

- 图片内容是否确实需要这么大的分辨率。
- 能否压缩后保持清楚；照片可按需求考虑 JPEG、WebP 等格式，透明图按实际情况选。
- 替代文字有没有说明图片内容。
- 是否有使用和公开发布的权限。
- 手机页面是否过宽，文字是否能看清。

只在 HTML 中把显示宽度改小，不代表下载文件也变小。public 图片通常需要自己先压缩。

### 7. 删图前怎么判断还在不在用

先在 VS Code 按 `Ctrl+Shift+F`，搜索文件名，例如 `a.jpeg`。查看文章、配置、友链数据是否引用了它。

还要考虑动态拼接的路径、其他项目或外部页面可能在用。搜索没有结果是线索，不是绝对保证。拿不准时先保留或备份。

不要看到“头像已经换了”就直接删光示例图片；它可能还被正文、横幅配置或教程演示引用。

## 十二、维护关于页、友链和站点信息

这一章是以后查位置用的，不要求现在把所有配置改一遍。

### 1. 修改 About，也就是关于页

在 VS Code 打开：

```text
src/content/spec/about.md
```

这里是关于页正文，按照 Markdown 写。保存后，在开发预览中打开：

```text
http://localhost:4321/blogFuwari/about/
```

成功时显示新正文。模板位于 `src/pages/about.astro`，负责读取关于页内容并放进布局；只想改自我介绍，不用改模板。

关于页不在 `posts` 中，不会因为编辑它就变成首页的一篇普通文章，也不需要照抄文章的发布资料栏。

### 2. 新增一条友链

“友链”就是指向其他朋友网站的链接。当前名单在：

```text
src/data/friends.ts
```

这是 TypeScript 数据文件，不是 Markdown。数组里的每个 `{ ... }` 表示一位朋友。

**下面只是一条待替换的数据示例，不是整个文件：**

```typescript
{
    name: '朋友的站名',
    url: 'https://example.com/',
    avatar: '/images/your-friend.jpg',
    description: '一句简短的介绍',
},
```

操作顺序：

1. 先准备真实站名、完整网址和介绍，替换示例文字；`example.com` 是示例地址。
2. 若使用本地头像，先把图片放进 `public/images`，再填写准确文件名。
3. 将这一整个对象放进现有 `friends` 数组，注意与相邻条目之间的英文逗号。
4. 保存，打开 `/blogFuwari/friends/` 检查卡片和跳转。

不要把整个文件覆盖成这一个对象，也不要把新对象写到数组结束的 `]` 外面。

当前 `src/pages/friends.astro` 会处理友链头像的根路径，给 `/images/...` 补站点前缀；数据中不用重复加 `/blogFuwari`。

### 3. 修改或删除友链

修改：找到对应对象，只改需要变更的字段。

删除：删掉对应完整对象，连同它作为分隔的一枚逗号，保持其他对象和外层数组完整。不要只删一半大括号。

保存后先看本地页面。页面标题或开头的说明文字则在 `src/pages/friends.astro` 中，不在名单字段里。

### 4. 导航、名称、简介、主题色在哪里

在 `src/config.ts` 中：

| 想修改的内容 | 对应位置 |
| --- | --- |
| 站点名称 | `siteConfig.title` |
| 站点副标题 | `siteConfig.subtitle` |
| 默认语言 | `siteConfig.lang` |
| 主题色 | `siteConfig.themeColor.hue` |
| 文章目录开关与深度 | `siteConfig.toc` |
| 顶部导航 | `navBarConfig.links` |
| 个人名字 | `profileConfig.name` |
| 个人简介 | `profileConfig.bio` |
| 头像 | `profileConfig.avatar` |
| 个人外链 | `profileConfig.links` |
| 横幅开关与图片 | `siteConfig.banner` |

导航里的站内路径会由导航逻辑处理 `base`，例如当前友链配置是 `/friends/`。这与文章正文手写链接不是同一个入口，不要所有地方一律手工加前缀。

配置里出现的官方 GitHub 链接，不会自动变成自己的仓库地址。是否要改成个人链接，应根据这条导航的实际用途决定。

### 5. 横幅不显示，先检查开关

当前 `siteConfig.banner.enable` 是 `false`。打开横幅需要以后自己决定是否改成 `true`，同时确认 `src` 图片存在。

渲染位置在 `src/layouts/MainGridLayout.astro`，外层有横幅开关判断。它不是靠“只在首页”这一项来决定是否存在；`isHomePage` 还参与页面布局和效果。

`banner.src`、`position` 和 `credit` 分别控制图片、裁切位置和图片署名。`credit.enable: false` 只是关闭署名，不是关闭整张横幅。

本篇重写不修改横幅、头像或全站样式。

### 6. 音乐分享链接，不等于播放器或音频文件

把音乐分享网址写成 Markdown 链接，读者可以点击去音乐平台。这是普通链接。

网页里的播放器需要真正可播放的音频地址，或平台正式提供的嵌入方式。分享页面网址、播放器页面、音频文件地址是三种不同东西。

当前没有接入专用音乐播放器和音乐解析接口。不要把分享地址直接塞进 `<audio src="...">` 就认为一定能播，也不要为此在文章里粘贴私人 Cookie 或令牌。

## 十三、一篇文章从写作到上线

这一章把前面的步骤串起来。命令都在项目根目录的 PowerShell 运行，示例文章仍使用 `my-first-note.md`；换文章时，路径和提交说明都要跟着换。

### 1. 新建草稿，先写内容

在 `src/content/posts` 创建文件，用前面的模板，先保留：

```yaml
draft: true
```

启动 `corepack pnpm dev`，保存后到开发预览看文章。这个阶段不用频繁提交或上传每一个错别字修改。

### 2. 检查正文、图片与手机阅读

至少检查：

- 标题与简介有没有写清楚。
- 段落、列表、提示块是否正常，文章末尾有没有被误吞进代码框。
- 图片能否打开，封面和正文图有没有混淆。
- 代码复制出来是不是自己预期的内容。
- 自动目录是否对应正确标题。
- 缩窄浏览器后，表格、代码和图片是否越过页面边缘。
- 深色、浅色模式里，局部文字颜色是否都看得清。

缩窄桌面窗口是方便的第一步；有条件时再用真实手机检查。`localhost` 不能直接发给另一台手机当公网地址。

### 3. 准备公开，再改开关

确认内容可以公开后，改为：

```yaml
draft: false
```

保存文件。别只改在编辑器里却忘了按 `Ctrl+S`。

### 4. 构建，再预览成品

```powershell
corepack pnpm build
```

成功后：

```powershell
corepack pnpm preview --port 4323
```

访问终端实际地址，检查首页和文章页都出现这篇文章。此时可以测试站内搜索，因为本次构建已经生成索引。

如果在构建预览改了文章，要先停止预览、重新 build，再重新 preview。它不会自动把新源码变成成品。

### 5. 检查差异，再提交

先看：

```powershell
git status
git diff
```

新文件还要在编辑器完整查看。只添加这篇文章和它实际用到的新增图片，不带入无关改动。

例如，只新增这一个 Markdown 文件时：

```powershell
git add -- 'src/content/posts/my-first-note.md'
git diff --cached
git status
```

确认暂存区内容正确，再提交：

```powershell
git commit -m '新增：我的第一篇记录'
```

提交之前已有的其他暂存内容也会一起进入提交，所以 `git diff --cached` 不能跳过。

### 6. 确认目标，再推送

```powershell
git remote -v
git branch -vv
```

确认仍在 `main`，`origin` 仍是 `Chalgen/blogFuwari`，并且当前提交就是准备发布的内容，再执行：

```powershell
git push origin main
```

这会触发当前配置中的 GitHub Pages 部署任务。无需把 `dist` 手工提交，也无需上传到另一个 `Chalgen.github.io` 仓库。

### 7. 去 GitHub 看这次是否真的发布成功

在浏览器打开当前仓库：

[Chalgen/blogFuwari](https://github.com/Chalgen/blogFuwari)

点击 **Actions**，找到名为 **Deploy preview to GitHub Pages** 的任务，再点开与这次提交对应的那一条。

| 看到的状态 | 意思和下一步 |
| --- | --- |
| 等待或排队 | 任务还没开始，稍后再看 |
| 正在运行 | 正在安装、构建或发布，等它结束 |
| 绿色成功 | 这次任务完成，再检查网站 |
| 红色失败 | 本次没有正常完成，需要看失败步骤 |
| `deploy` 被跳过 | 前面的构建可能失败，尚未发布这次成品 |

GitHub 上可能同时有多个检查任务。要分清**部署任务本身**与其他代码检查；不能只看到某处有一个红叉或绿勾，就判断网站一定发布或一定没有发布。

若失败，进入 `build`，展开失败的步骤，找第一个明确的错误。末尾“Process completed with exit code 1”只表示失败，不解释原因。

**失败以后，继续等待不会让同一次失败自动变成成功。** 网站可能仍然显示前一次成品，所以会有“GitHub 文件改了，网页却没变”的情况。先修复实际问题，再重新运行或提交修复；不要反复改文章日期碰运气。

### 8. 最后检查线上页面

当前预览站地址是：

[https://chalgen.github.io/blogFuwari/](https://chalgen.github.io/blogFuwari/)

本篇文章的线上路径是：

```text
https://chalgen.github.io/blogFuwari/posts/blog-handbook/
```

等对应部署成功，再打开网站，检查首页、文章、图片和搜索。必要时按 `Ctrl+F5` 强制刷新，或使用浏览器无痕窗口排除旧缓存。

部署过程中确实要等任务完成，但不承诺每次固定几秒或几分钟。以任务结果与实际线上页面为准。

### 9. 当前站点地址与子路径的配置

在 `astro.config.mjs` 中，当前是：

```javascript
site: 'https://chalgen.github.io',
base: '/blogFuwari',
```

`site` 是完整站点地址所用的域名来源；`base` 表示站点放在域名下的哪一段路径。

当前是 GitHub Pages 项目站，所以浏览器地址里有 `/blogFuwari/`。RSS 和 sitemap 的完整链接也应使用这个域名和路径。**不需要为了每篇新文章修改它们。**

`base` 会影响构建工具生成的 CSS、JS 等资源链接，以及项目使用辅助函数生成的导航和图片地址；不会神奇地重写每一段文章里的手写 HTML 或根路径。

RSS 是给订阅工具阅读的文章更新信息；sitemap 是供搜索引擎了解站点页面的清单。当前输出位置分别为 `/blogFuwari/rss.xml` 和 `/blogFuwari/sitemap-index.xml`。

当前文章模板没有单独生成 canonical 链接标签。以后若加入这种“首选页面网址”标记，也要核对完整域名和子路径，不要只看首页能打开就认为所有网址都正确。

当前工作流已配置 Node 22、pnpm 构建和 GitHub Pages 发布。配置文件存在，不代表任意一次运行都会成功。本文不把尚未成功的那次部署写成已上线，也不涉及绑定其他域名。

## 十四、常见问题：先看现象，再查原因

### 1. 找不到 package.json

先运行 `Get-Location`，确认不是在桌面、父目录或文章目录。

```powershell
Set-Location 'C:\code\blog-astro'
Test-Path .\package.json
```

显示 `True` 再运行项目命令。如果连这个目录都不存在，先确认项目实际放在哪里，不要按旧位置重复输入。

### 2. 提示找不到 Astro 或依赖

先确认工具命令存在，再在项目根目录安装：

```powershell
corepack pnpm install
```

安装成功后再启动。不要自己新建一个 `node_modules` 文件夹来“补齐”，也不要先删锁文件。

### 3. 安装因网络失败

先读报错，区分超时、连接失败、证书问题和版本冲突。网络超时不等于文章有问题。

确认网络、代理或组织网络设置后，重试原来的安装命令。不要为了连上网络就关闭证书校验，也不要为了消除报错同时升级所有依赖。

如果 `corepack` 首次调用需要下载 pnpm，它本身也可能因网络失败；这发生在真正安装项目依赖之前。

### 4. YAML 解析错误

优先检查文章最上面的资料栏：

- 开头和结尾的 `---` 是否齐全。
- 冒号是否英文，后面有没有空格。
- 引号是否成对，是否混进中文弯引号。
- `tags` 是否数组，`category` 是否一段文字。
- 日期是否有效，`draft` 是否没有加引号的开关值。

可以先缩减成最小模板，再逐项补回。不要一次改十处，导致不知道是哪一处修好了问题。

### 5. 文章不出现

按顺序检查：

1. 文件是否保存到了 `src/content/posts`，后缀是不是 `.md`。
2. 资料栏是否通过检查。
3. 是否仍然 `draft: true`；开发能看见、成品看不见正是草稿规则。
4. 打开的是本地开发、构建预览，还是线上；有没有忘记 `/blogFuwari/`。
5. 本地成品是否重新构建过。
6. 改动是否已经提交、推到正确分支。
7. 对应 GitHub Pages 部署是否成功。

**不要一看到线上没文章，就把本地文件删掉重建。**

### 6. 图片不显示

先确认文件存在，再检查路径起点、大小写和扩展名。

正文的 `/images/...` 在当前子路径站点可能指错位置；普通 Markdown 要检查 `/blogFuwari/images/...`，组件配置则看是否已经自动补 `base`。

图片网址打不开是路径或资源问题，不能靠改替代文字修复。外链图片还要考虑对方删除、防盗链和网络问题。

### 7. 代码块或 Markdown 突然乱了

如果从某一处开始，后面整篇都变成代码，先检查这一处上方的代码围栏有没有结束。

列表乱缩进时，检查是不是混入 Tab 或全角空格。HTML 后面的排版异常时，检查标签是否闭合，以及是否把 Markdown 放到了不会继续解析的 HTML 块里。

先回到最近一个正常位置，分小段恢复，比全篇随机替换更容易定位。

### 8. 本地构建失败

看终端第一个具体错误，以及它提到的文件和行号。常见原因是资料栏写错、图片找不到、页面代码出错。

如果只有线上失败、本地成功，要检查 GitHub 上的文件是否齐全、大小写是否一致、锁文件与依赖是否匹配，以及工作流具体失败在哪一步。

警告不一定是错误。不要看到依赖更新提示就立刻大升级，也不要用“本地成功”断言线上必然没问题。

### 9. 搜索搜不到

先确认文章不是草稿，再运行完整 `build`。只启动 `dev`，不代表搜索索引一定已经更新。

在构建预览中尝试标题中的短词和正文中的独特词。公式节点或明确标了忽略的内容可能不参与索引。

如果线上搜索还是旧的，再查部署与缓存。不要把“索引里没有草稿”误判成中文不支持。

### 10. 保存了，预览却没变

先确认按了 `Ctrl+S`，再看预览服务是否还在运行。

检查浏览器是否打开了错误端口、另一个项目或线上网站。`preview` 读取旧 `dist` 时，要重新构建；改了配置后，开发服务有时需要重启。

页面切换与浏览器都可能保留缓存，确认前面步骤后再强制刷新。缓存不是所有问题的默认答案。

### 11. Git 提示没有提交身份

Git 提交需要记录作者名称和邮箱。它们不是登录密码，也不会替你登录 GitHub。

先查看当前设置：

```powershell
git config --get user.name
git config --get user.email
```

如果需要只给当前仓库设置，在项目目录执行下面命令，**把引号里的占位内容换成自己的真实选择，不要照抄**：

```powershell
git config user.name '替换为你的提交署名'
git config user.email '替换为你决定用于提交的邮箱'
```

公开仓库的提交记录会公开这项身份信息。若想保护私人邮箱，可先去 GitHub 账户的邮箱设置查看平台提供的隐私邮箱，再填写自己的对应值。

## 十五、写错了怎么恢复：先分清改动在哪一层

恢复前先做两件事：**复制一份重要内容到仓库外的备份位置，再看 `git status`。** Git 不一定有你还没提交过的新内容。

### 1. 还没暂存：只想撤掉某个已跟踪文件的修改

先看这个文件改了什么：

```powershell
git diff -- 'src/content/posts/blog-handbook.md'
```

**下面的恢复命令会丢弃这个文件尚未暂存的修改。确认不需要这些内容后再执行：**

```powershell
git restore -- 'src/content/posts/blog-handbook.md'
```

它通常把工作区恢复为暂存区对应内容；若没有暂存过，这通常就是最近提交的版本。它不是“只撤销最后一次打字”，而可能撤掉一大段尚未保存进 Git 的写作。

只想退一两步编辑操作，先考虑编辑器的 `Ctrl+Z`，并确认恢复结果。

### 2. 已暂存，还没提交：只想退出本次提交清单

```powershell
git restore --staged -- 'src/content/posts/blog-handbook.md'
```

这个动作**保留工作区修改**，只取消暂存。之后可以继续编辑或重新添加。

取消暂存与丢弃内容是两回事，不要把这一步与上一节的 `git restore` 混为一谈。

### 3. 新建的未跟踪文件

新文章如果从未提交，Git 未必有可恢复的历史。普通 `git restore` 不能凭空还原这些内容。

不想保留时，可以先把它移到仓库外备份，再通过编辑器删除确定不需要的文件。误删后，先查回收站、编辑器本地历史或自己的备份。

不要用批量清理命令来处理一篇不确定要不要保留的新文章。

### 4. 已经提交，但还没推送

先用 `git log -5 --oneline` 找到提交，再用 `git show 提交编号` 确认内容。

如果只是把一个句子改错了，最直观的办法是把它改回来，重新检查，再提交一次。历史会清楚地记录“改错”和“修正”。

若需要撤销某个完整提交，可以使用 `git revert 实际提交编号`。它会尝试创建一个反向修改的新提交，可能需要处理冲突。**这不是点一下就必然安全的万能撤销**；先确认工作区状态、目标提交和影响范围。

不要拿 `vanilla` 当作“我的上一版”，也不要为了退一篇文章而把整个仓库回到很早的状态。

### 5. 已经推送

通常优先新增修正提交，或在确认影响后用 `git revert` 撤销目标提交，再按正常流程发布。

已经公开的历史可能被其他设备或协作者使用。不要默认重写历史，也不要默认强制推送。

`git reset --hard` 会让相关未保存改动丢失，`git clean` 可以删掉未跟踪文件，强制推送可能覆盖远程历史。它们都不作为这里的初学者日常修复方法。

### 6. `vanilla` 标签是什么意思

**标签**是给某个固定历史版本起的名字，和持续向前发展的分支不同。

本项目有 `vanilla` 这个原版基线标签，帮助辨认主题的原始状态。它不表示“当前个人博客最新备份”，也不保证包括后来加入的友链、头像、文章和部署设置。

**“回到 vanilla”不是日常撤销操作。** 真正恢复时，应找到想恢复的具体文件和具体提交。

## 十六、搜索、备份和长期维护

### 1. 搜索为什么要等构建

本项目的完整构建命令包含：

```text
astro build && pagefind --site dist
```

意思是先成功生成网页，再为 `dist` 建立 Pagefind 索引。草稿没有进入成品，也就没有可供它索引的正式文章页。

正确的检查方式是：公开文章后构建、启动成品预览、在搜索框查标题和正文关键词。可以用本篇的“这个博客怎么用”“暂存区”“替代文字”等词测试。

Pagefind 提示 `zh-cn` 不支持 stemming 时，指的是它没有对应的词形还原能力，不应直接解释成“中文完全搜不了”。某个词是否命中，要实际验证；也不要没测就先加一套中文分词插件。

索引生成、浏览器搜索交互、线上部署是不同环节，一个环节成功不代表所有环节都完成。

### 2. 日常怎么备份

最少保留两份：电脑上的项目，以及推送到自己 GitHub 仓库的提交。提交只在本机，还不是另一台设备上的备份。

未跟踪文件、未提交文字，以及被忽略的文件，不会因为一次 push 自动上传。特别重要的长文还可以另存一份到自己信任的备份位置。

公开仓库不是私密笔记本；备份私人内容时要选合适的位置。

### 3. 依赖升级不要一次全做

`package.json` 说明需要什么依赖，`pnpm-lock.yaml` 锁定实际版本。升级时要把它们作为一组看待。

想升级某个依赖，先弄清为什么需要，再看兼容说明，做小范围改动，预览并构建。不要为了消除“有新版本”或浏览器数据较旧的提示，一次升级所有包。

`format` 和 `lint` 也不是单纯只读检查：本项目脚本带有写入参数，可能改动整个 `src`。日常写一篇文章，不需要为了“保险”每次运行它们。

### 4. 更新上游 Fuwari，要与写作分开

`upstream` 当前指向官方主题。更新主题意味着把官方变化带入个人项目，不是把自己的文章推给官方。

先保证个人内容有提交和备份，查看官方改了什么，再考虑合并。主题更新可能影响配置、页面、依赖和样式；与新增文章分开做，出问题更容易找原因。

不熟悉冲突处理时，不要把一长串“获取、重置、强推”命令当升级教程照抄。

## 十七、文末速查：下次忘记时看这里

### 1. 日常写文章的最短步骤

1. 用 VS Code 打开 `C:\code\blog-astro`。
2. 在项目根目录启动 `corepack pnpm dev`。
3. 在 `src/content/posts` 新建或编辑 `.md`，先用 `draft: true`。
4. 保存，检查文字、图片、代码、目录和手机宽度。
5. 准备公开后改 `draft: false`，运行 `corepack pnpm build`。
6. 用 `corepack pnpm preview` 检查成品。
7. 检查 Git 改动，添加指定文件，检查暂存区并提交。
8. 确认仓库与分支后推送，检查对应部署成功，再检查线上网站。

**不是每次都要安装依赖，不是提交就会上线，也不是推送成功就能跳过部署检查。**

### 2. 常用命令表

以下都是项目根目录下的 PowerShell 命令，涉及文件的路径要换成实际目标：

| 命令 | 用途 |
| --- | --- |
| `Get-Location` | 看当前目录 |
| `Get-ChildItem` | 看当前文件 |
| `corepack pnpm install` | 首次或需要时安装依赖 |
| `corepack pnpm dev` | 开发预览，包含草稿 |
| `corepack pnpm build` | 生成成品与搜索索引 |
| `corepack pnpm preview` | 查看已经构建的成品 |
| `corepack pnpm check` | 运行 Astro 检查，不能代替构建 |
| `corepack pnpm new-post 文件名` | 新建文章，留意默认公开 |
| `git status` | 看分支和文件状态 |
| `git diff` | 看已跟踪文件未暂存的修改 |
| `git diff --cached` | 看这次准备提交的内容 |
| `git log -5 --oneline` | 看最近五个提交 |
| `git remote -v` | 看远程地址 |
| `git branch -vv` | 看分支与跟踪关系 |

暂存、提交、推送不能只背一个通用命令表，涉及具体目标，按“用 Git 保存版本”和“从写作到上线”两章逐步核对。

停止持续运行的预览：在对应终端按 `Ctrl+C`。

### 3. 最小草稿模板

**文件内容，不是终端命令。日期、标题、正文都需要按实际替换：**

```markdown
---
title: '在这里填写文章标题'
published: 2026-10-26
draft: true
---

这里写开头。

## 第一个章节

这里写正文。
```

没有封面不必添加；使用完整模板时写 `image: ''` 即可。
